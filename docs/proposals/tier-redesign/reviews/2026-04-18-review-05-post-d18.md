# STC Proposal — 5차 리뷰 (D-18 + Write-mode Pilot)

## 요약 (Executive Summary)

D-18(Component = 데이터 진입점 + 6 sub-type taxonomy)은 **진단으로서는 정확**하다. 4차 리뷰가 "Component 과부하"로 지목한 긴장이 "본래 의도의 명시화"로 재해석되며, meta-semantic Data 개념(Data IR, 5 facet 역할)을 STC Component sub-type과 매핑하는 표(`03-decisions.md:264~270`, `tiers/component.md:97~102`)는 STC ⊥ meta-semantic 직교성 주장에 실질 근거를 준다. 6 sub-type 정의는 `tiers/component.md:22~35`, `03-decisions.md:253~261`, `rules/classification.md:68~77`, `mental-models.md:40` 네 곳에서 **동일 리스트 + 동일 후보 상태 (validation-rule / constant-literal)**로 공유되어 cross-file 일관성이 양호하다. 그러나 **실행 완결성은 또다시 부분**이다 — Pilot 5종 중 2종이 가상이라 pilot network의 "증거 밀도"가 희석되었고, `approval-system.md:16`의 `implements_type: write-mode` 필드는 `03-decisions.md`/`rules/*`/`tiers/system.md` 어디에도 공식 정의가 없어 **신규 frontmatter field가 Pilot에서 선도입**된 상태다. 가상 `depends_on: notification-system (가상)` 패턴과 가상 pipe 경로(`meta-semantic/pipe-impl/approval-pipe#...`)는 방법론적으로 **실제 meta-semantic 문서 구조와 다를 가능성**(실 meta-semantic pipe 문서는 `.spec.md` 확장자 + frontmatter `^defines`/`^purpose` 마커를 쓰는데 가상 경로에는 path 형식의 fragment `#...`만 있음)이 있다. **Verdict: `yes-with-minor-polish`** — D-18은 수용 가능, write-mode Pilot은 긴장 3을 **부분 해소** (개념 시연은 효과적이나 실증 공백은 유지), under-review 승격 전 `implements_type` 공식화 + 가상 Pilot의 한계 배너 강화 + 삭제 누락 검증 항목 2~3건이 권장되나 차단자는 아님.

## Verdict

- **Ready for under-review**: `yes-with-minor-polish`
- **D-18 평가**: `successful` (개념적 타당성 + cross-file 일관성 모두 양호)
- **Write-mode Pilot 평가**: `partial` (패턴 시연은 효과적이나 "가상" 성격이 실제 검증 가치를 희석, `implements_type`의 비공식 도입이 구조적 문제)
- 핵심 근거:
  1. D-18이 긴장 1("Component 과부하")을 재해석으로 근본 해소한 것은 설계 관점에서 **정직한 판단**. 이중 소유 문제도 "meta-semantic 영역에 유지, STC는 tier taxonomy 관점 분류" 원칙으로 명료화됨(`tiers/component.md:13~19`, `03-decisions.md:272~275`).
  2. Write-mode Pilot은 긴장 3을 **부분적으로만** 해소. 실제 meta-semantic pipe 문서(`approval-pipe.spec.md`) 미작성을 3곳(`approval-system.md:18~20 frontmatter 주석 + :31~37 배너 + :216~222 공백 섹션`)에서 명시해 투명성은 확보했으나, 가상 vs 실재의 비율(2:3)은 pilot 네트워크의 실증 밀도를 낮춤.
  3. `implements_type` 필드가 `approval-system.md:16`에 선도입됐는데 공식 정의 위치가 없음. `rules/state-machine-delegation.md`와 `tiers/system.md`에서 `read_only_projection` 필드가 이미 같은 기능(`: true/false`)을 제공하므로 **중복 또는 의도적 세분화**인지 불명확.

### 2.6 Compensate 예시 현실성

**approval-system.md:81~99의 compensate 예시**:
```yaml
body:
  sequence:
    - step: validate-approver-permission
    - step: db-update-status-to-approved
    - step: emit-approval-event
    - step: send-notification-to-requester
compensate:
  sequence:
    - step: revert-db-status
    - step: mark-event-as-invalid
    # notification은 역전 불가 — best-effort로 skip
```

**평가**:
- **구조적 적절성**: meta-semantic `PipeTransitionScope.compensate` 개념과 일치. `docs/specs/meta-semantic/pipe-impl/transition-scope.spec.md:49~50`에 `compensate?: PipeFlow` 정의 실재. Pilot의 `compensate.sequence: [...]`는 이 구조를 따름.
- **현실성**: step 이름이 **prescriptive**지 descriptive 아님 — `validate-approver-permission`, `db-update-status-to-approved` 같은 가상 step 이름은 실제 meta-semantic pipe가 담을 step 타입(`PipeCompensate`, `PipeEmit` 등)이 아닌 **도메인 specific action name**. 실제 meta-semantic pipe 구현에서는 step이 30종 PipeFlow 중 하나를 참조하는 구조인데 Pilot의 가상 step은 그 계약을 따르지 않음.
- **notification 역전 불가 주석**: `# notification은 역전 불가 — best-effort로 skip` — 이 주석은 **실제 운영에서 의미 있는 관찰**. DB는 revert 가능하나 외부 알림은 "보낸 것을 안 보낸 걸로" 할 수 없음. 이 현실적 감각은 Pilot의 질을 올림.

**권장**: step 이름을 "PipeFlow 30종 중 어느 유형"인지 주석화하거나, 가상 step임을 명시. 예: `- step: validate-approver-permission  # meta-semantic PipeBranch 또는 PipeFilter 예상`.

**단 심각도**: Low. 가상 Pilot이라는 배너가 명확하므로 step 이름의 구체성 부족은 patterns 시연 목적에 지장 없음.

### 4.4 Compensate의 STC 진입 여부

**현황**: `approval-system.md:81~99`에 compensate 구조 서술. 그러나 STC 어디에도 compensate 개념 정의 없음:

**긴장**: Pilot에서 compensate를 사용하지만 STC는 compensate를 모름. Consumer가 Pilot 읽으면 compensate를 **STC 개념으로 오해**할 여지.

**해석 1 (D-17 원칙 준수)**: compensate는 meta-semantic 내부 — STC는 `pipe_refs` 참조만으로 충분. Pilot이 meta-semantic pipe content(compensate 포함)를 "예시"로 보여줄 뿐 STC concept는 아님.

**권장**: `approval-system.md:81~99`의 compensate 예시를 **meta-semantic 측 문서(가상 `approval-pipe.spec.md`)로 이관**하는 것이 이상적. 현 Pilot에서는 "예시 참조" 수준으로 축소하고 meta-semantic 문서 작성 시점에 full content로 전환.

**대안 (최소 수정)**: `approval-system.md:81` 상단에 "**⚠️ 아래 구조는 meta-semantic 측 문서(가상 `approval-pipe.spec.md`)에 실제로 담길 내용을 **참고용으로 예시**. STC `approval-system.md`는 `pipe_refs` 참조만 담고, 실제 compensate/body는 meta-semantic 영역 소유**" 같은 명시 추가.
