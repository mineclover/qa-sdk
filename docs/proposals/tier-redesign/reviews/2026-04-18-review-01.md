# STC Proposal Review — 2026-04-18

## 요약 (Executive Summary)

STC 제안은 ECS/UML 패턴을 문서 분류에 이식한 개념적으로 탄탄한 설계이며, Phase 0 결정 메모(D-1~D-14) + Pilot 예시 3종이 서로를 지지하는 구조적 완결성을 보인다. 특히 FSM tier의 spine+heading mirror 패턴과 Guard/Quality Gate 구별, System 독립성 원칙은 실효성이 높다. 다만 **Entry tier를 제거하지 않고 유지하면서 동시에 "사용 신중" 라벨을 붙여 모든 문서에 반영한 결정은 self-inconsistent**하고, **R-7 3-check가 "모호성 해소 도구"로 과대평가**되어 있으며, **Pilot 관찰 6개의 "해소"는 실제로는 "결정 선언"에 가깝다** (관찰 자체는 Pilot 실행 후에야 닫힘). 전체 평가는 **`no-with-revisions`** — 개념적으로는 under-review로 승격 가능하지만 3~4건의 blocker/important 이슈를 명시적으로 정리한 뒤 올려야 리뷰어가 효율적으로 검토할 수 있다.

## Verdict

- **Ready for under-review**: `no-with-revisions`
- 주요 근거:
  1. Entry tier의 양가적 지위(유지하지만 사용 신중)로 인한 문서 내 중복 경고 및 R-2 미결정. Phase 0에서 Option A/B/C 중 하나를 고르지 않은 것은 Phase 0의 목적 — "고정"에 반함.
  2. Pilot "해소 완료" 6개 중 일부(D-12 evidence promote, D-13 consumer 참고 표준)는 Pilot 관찰 없이 선언된 컨벤션이라 real burden을 아직 모름. 제안 자체는 "Pilot에서 검증"이라 하면서도 "해소 완료"로 표기된 상태가 불일치.
  3. 자동 분류 성공률 ≥ 80% 목표가 DKG CON-004와 "정렬"한다 기술되었으나(01-migration.md §Phase 2), 실제로는 두 분류 체계가 직접 연결되지 않음 — 근거 인용이 약함.

## Category A: 개념 일관성 (README Checklist §1~4)

### A-1: 5 tiers 정의 간섭 없는 설명력

- Status: **의견**
- 근거:
  - `tiers/component.md` vs `tiers/entry.md` 경계: Entry는 "Component의 instance"(component.md §Entry와의 관계)이면서 동시에 "canonical singleton 인스턴스 패턴"(entry.md §Entry 후보가 될 수 있는 경우)으로 정의된다. 두 정의의 교집합이 좁아 "Entry는 뭐지?"라는 질문에 두 문서가 약간 다른 답을 준다.
  - `tiers/fsm.md` § 정의 ("Entry의 생명주기를 선언적으로 정의하는 composition tier")와 § 핵심 원칙 §1.4 ("System의 소비 인터페이스") 사이 **성격 충돌**은 없지만, 독자가 어느 쪽을 primary mental model로 삼을지 불명확. §1.4가 우선이라는 선언이 더 분명하게 필요 (현재는 "목적은 consumer-facing contract"라는 한 문장뿐).
  - 5 tier가 **서로 간섭**하는 경우 (예: "FSM과 System 동시 후보 → 두 문서로 분리"는 `rules/classification.md § 애매 케이스 해소`)는 처리되어 있으나, 실제 많이 나올 "Component와 FSM 동시 후보"(예: states를 정의한 Component)는 missing.
- 개선 제안:
  1. `tiers/entry.md` 앞부분에 "Component의 runtime instance ≠ Entry tier 문서 대상"을 더 분명히 선언. Entry = **문서화할 가치가 있는 singleton instance pattern**이라는 단일 정의를 제시.
  2. `tiers/fsm.md`의 § 정의와 § 핵심 원칙을 순서 교체 — consumer 인터페이스 관점을 먼저 노출.
  3. `rules/classification.md § 애매 케이스 해소`에 Component-FSM 공존 케이스 추가.

## Category B: Pilot 예시 검증 (README Checklist §5~7)

### B-1: FSM 예시의 실제 코드 대응 가능성

- Status: **의견**
- 근거:
  - `examples/deterministic-label-record-fsm.md` 의 7 states(DRAFT/LINTED/RESOLVED/ACTIVE/DEPRECATED/ARCHIVED/BLOCKED)는 `packages/cli/src/lib/docs-control-plane/deterministic-labels.ts` + 관련 fsm 로직과 매핑될 것으로 보이나 **mapping 증거가 문서에 부재**. `implementation_refs` 필드(D-9.1에 언급)가 frontmatter에 아직 빠져 있음.
  - BLOCKED state가 "예약 — 현재 read-only projection에서는 절대 할당되지 않음"(line 132-136)은 합리적이나, 이것이 FSM frontmatter `states[]`에 포함되어 있으면 "현재 시스템에서 도달 불가능한 state를 문서화"하는 것 → SSOT 방향에 긴장. D-9 "code가 문서를 따른다"인데 코드에는 이 state가 없을 수 있음(또는 있지만 할당 경로 없음). 문서 ↔ code 일치 검증 시 어떻게 처리될지 스펙 없음.
  - `event-lint-guard-passed` / `event-resolve-guard-passed` / `event-active-guard-passed` 세 이벤트는 모두 "Guard 통과를 관측한 Event"(`tiers/fsm.md § Event vs Guard 관계`의 "관측 이벤트" 패턴)인데, 이 패턴이 FSM 전체에 적용된 구조 — Guard 없이는 Event도 trigger 안 됨. 실제 코드가 Event/Guard 구별을 가지고 있는가? 코드는 아마 단일 `computeReadiness`가 Guard 평가 + state 결정을 한 번에 하는 구조일 텐데, 그러면 FSM 문서의 Event 개념이 코드에 직접 대응되지 않음.
- 개선 제안:
  1. FSM frontmatter에 `implementation_refs: [packages/.../deterministic-labels.ts, ...]` 추가. D-9 validate-time 매핑 실전 적용.
  2. BLOCKED state 관련 § BLOCKED ^state 앞에 "⚠️ code 측에는 enum member로 존재해야 하는가?"를 섹션으로 명시. D-9 SSOT 방향에서 "코드에 없어도 되는 state"를 문서에 선언할 때의 validate 예외 규칙 정의.
  3. "관측 이벤트 패턴"이 FSM 전체 설계인 점을 FSM 예시 상단에 명시. Consumer가 Event 4개 중 3개가 사실상 Guard passed signal이라는 걸 바로 이해 가능하도록.

### B-2: System 예시 R-7 3-check 3/3 평가 타당성

- Status: **의견**
- 근거:
  - `examples/deterministic-label-system.md § R-7 3-check 자가 검증` 표(line 44-50)는 3항목에 ✓를 달고 있으나:
    - **명명 가능성** ✓ 근거: "consumer가 이 이름으로 부름" — 자체 추론, 외부 증거 없음 (어떤 consumer가, 어디서 이 이름을 쓰는지 인용 없음).
    - **독립 운용** ✓ 근거: "CLI `docs-control-plane`의 하위 System으로, 단독으로 ... 결과 제공" — 그런데 "CLI의 하위 System"이라는 말은 **독립 운용과 다소 모순**. 하위라는 것은 embedded라는 의미이고, "독립 운용"은 endpoint 역할을 요구. `depends_on`만으로 운용되는지, CLI wiring 없이 단독 invoke 가능한지 명확치 않음.
    - **Lifecycle 유무** ✓ 근거: FSM implements. 이건 논리적으로 circular — "System이 FSM implements이니까 lifecycle 있고, lifecycle 있으니까 System이다." 
  - 근본 문제: R-7 3-check는 **System vs not-System**을 구별하는 도구로 제안됐는데, Pilot 예시에서는 이미 System이라고 전제하고 3/3을 채점. Sanity check가 실질 구별력을 보여주지 못함.
- 개선 제안:
  1. R-7 3-check를 적용할 때 **"System이 아닐 수 있는" 반례**를 함께 검토. 예: "만약 이것이 Component + 3개 함수 집합이라면 어떻게 다를까?" 형식의 counter-test.
  2. **독립 운용** 기준을 더 precise하게 풀어쓰기. "endpoint 역할"이 모호 — "외부 consumer가 호출 가능한 표면을 갖는가?" 정도로.
  3. Pilot 예시 § R-7 3-check에서 각 항목에 externalizable evidence(코드 경로, caller 참조, CLI subcommand)를 인용.
