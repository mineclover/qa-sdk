### 공통 구조

각 시나리오는 Wave 1 seed 그대로 4요소 유지:

1. **전제** — 부모 시스템이 제공하는 계약 상태
2. **동작** — 자식이 트리거하는 호출 경로
3. **기대** — 자식이 의존하는 결과 (계약의 본질)
4. **실패 시 수정 대상** — 1줄, 어느 부모 스펙 어디를 고쳐야 하는가

## Wave 1 관찰된 이슈: scope + aspect 유효 조합

### 발견

Wave 1 의 12개 `.cases.md` 중 **5건만 DB 에 등록**, 7건은 scope-aspect validation 에서 silently 거부되었다. `vocabulary.ts` + `taxonomy.ts` 의 `VALID_SCOPE_ASPECTS` 매트릭스는 `aspect: user_scenario` 를 `scope: flow` 에서만 허용한다.

| aspect | 유효 scope |
|---|---|
| user_scenario | flow |
| scenario | feature |
| func_def | feature |
| api_contract | interface |
| ... | ... |

Wave 1 에서 `scope: feature`, `data`, `interface` 로 작성된 `.cases.md` 는 `sync` 시 scan error("scope \"X\" + aspect \"user_scenario\" 조합 유효하지 않음") 로 drop.

### Wave 2 대응

모든 Wave 2 `.cases.md` 는 `scope: flow` + `aspect: user_scenario` 로 고정. Wave 1 조합 오류 7건은 Wave 3 에서 수정 (이번 PR 범위 외 — 파괴적 변경 최소화).

### 권장 후속 조치

1. Wave 1 7건 frontmatter 수정 (`scope → flow`, ID 변경 없음, address 재계산 필요)
2. `sync` 커맨드가 scan error 를 stderr 로 출력하도록 강화 (현재는 grep 해야 보임)
3. `skill-creator` / `def-new` 스킬에 `.cases.md` 기본 `scope: flow` 규약 명시

## 발견된 이슈

### 1. Wave 1 `.cases.md` 중 7건이 DB 에 미등록

위 "Wave 1 관찰된 이슈" 섹션 참조. Wave 1 보고서의 "85.7% 커버리지" 주장은 파일 기준이며, DB 기준 실제 등록은 5/14 (36%). `def sync` 의 silent scan error 정책이 이를 가려왔다.

### 2. 시나리오 유효 조합 제약 (scope-aspect)

`user_scenario` aspect 는 `scope: flow` 에서만 유효하지만, 소비 시나리오의 성격은 자식의 원래 scope(feature, data, interface 등)에서 비롯된다. 이 제약이 `tier: component` 로 강제되어 소비 시나리오가 원래 scope 와 분리된 좌표를 갖는다.

**의미 해석**: `.cases.md` 는 *consumer-driven 계약 flow* 이므로 `flow + user_scenario` 가 의미론적으로 정확(사용자→시스템 호출 흐름). parent 의 scope(feature 등)와 무관하게 "이 의존의 사용자 흐름" 으로 분류하는 것이 옳음.

**후속**: 00-design §2.5 또는 skill 가이드에 이 규약을 명시 (현재는 Wave 1 암묵 관례).

### 3. root-shell spec 의 시나리오 도출 불가

`viz-system-root`, `dkg-system-root`, `decode-service-spec` 등 2줄 shell spec 은 concrete contract 가 없어 시나리오가 parent spec 재선언이 됨. 이 경우 "실패 시 수정 대상" 이 항상 parent-root 자체가 되어 1-line 지침 품질 저하.

**대응 방침**: root-shell 은 Wave 3 에서 parent spec 확충 후 진행. 강제 작성 시 boilerplate 가 Wave 1 §1 이슈와 동일.

### 4. `.cases.md` orphan 정책 명시 필요

Wave 1+Wave 2 합산으로 orphan warning 27건 중 23건이 `.cases.md` (정상 상태). `def audit` 가 `*-cases` suffix 패턴을 orphan 면제 대상으로 인식하도록 linter 확장 제안 (Phase 6 CLI).
