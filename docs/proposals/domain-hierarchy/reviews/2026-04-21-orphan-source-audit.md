# Orphan Source Audit — 309 파일 분류 (2026-04-21)

## 목적 ^purpose

`def doctor` 가 보고하는 **source coverage 81.3% (1340/1649)** 의 분모/분자 신뢰성을 확인하기 위해 309 건의 orphan source file(`@def.boundary` / frontmatter `source:` 연결이 없는 `packages/*/src/*` 파일)을 heuristic + content sampling 으로 4 범주(A/B/C/D)로 분류한다. 이 분류는 (1) 현실적 coverage 목표 재조정, (2) 자동 수정 가능한 gap 목록 확정, (3) `collectCodeLinkCoverage` 로직 개선 제안의 근거가 된다.

## 분석 방법 ^method

- 원천 데이터: `pnpm exec qa-sdk def code-link-gaps --json=true --limit=5000` → 309 경로.
- 분류 규칙 (우선순위 순):
  1. `*/__mocks__/*` → **A** (mock fixture)
  2. `*/synced/*` → **A** (mirrored service source; 원본 스펙은 upstream 서비스가 보유)
  3. `*/scenarios/*` → **A** (test scenarios fixture)
  4. 패키지 전체가 harness/smoke/bench 용인 경우(`simulation-tests`, `facet-tests`, `viteplus-sdk-smoke`, `bench`) → **A**
  5. 파일 상단 25 라인에 `@generated` 또는 `Code generated by` 마커 → **B**
  6. 파일 상단 25 라인에 `describe(`/`test(`/`it(`/`bench(` 이 export 없이 등장 → **A** (inline test content)
  7. `src/{index,main,app,server,client,service,worker}.ts` → **C** (package/service entry)
  8. `src/{routes,controllers,handlers,services,commands,engine,domain}/*` → **C** (business-structure directory)
  9. `src/.../(types|utils|helpers|constants|errors|logger|schema|schemas|config|repository|migrate|migration|state|model|presets|examples|io).ts` → **D** (utility/support)
  10. 그 외 `packages/*/src/*` → **C** (기본 비즈니스 로직 후보)

- 내용 샘플링: 각 범주 3~5 건 머리 25 라인을 확인해 오분류 유무 검사. `convergence`, `decision-flow`, `event-catalog` 등 비즈니스 코어는 모두 실제 구현 모듈로 확인.
- 노트: `collectCodeLinkCoverage` 는 기본적으로 tests/dist/node_modules 를 이미 제외한다(`src/` only, test regex). 따라서 **B(generated) 는 실측상 0 건**이다 — 현재 리포지터리는 generated 코드를 `dist/`에 모으고, 남아있던 한두 개 `.d.ts` 유사 파일은 TEST/INCLUDE 필터 단계에서 이미 걸러진다.

## Realistic Coverage 재계산 ^adjusted-coverage

현재 수치는 분모에 A(infra)를 포함하여 실제 "연결해야 할" 코드의 비율을 과소평가한다.

| 지표 | 값 |
|---|---:|
| `def doctor` 원시 수치 | 1340 / 1649 = **81.3%** |
| A(infra) 자동 제외 시 분모 | 1649 − 105 = 1544 |
| **조정된 현재 coverage** | 1340 / 1544 = **86.8%** |
| C 를 모두 해소한 경우 | (1340 + 176) / 1544 = **98.2%** |
| C + D 모두 해소한 경우 | (1340 + 176 + 28) / 1544 = **100%** |

즉 진짜 gap 은 **176 건 (11.4 pt)** 이며, 현실적 단기 목표는 `>= 95% (= 1466/1544)` → C 중 130 건 우선 해소.

## 제안 ^proposals

### 제안 1 — `collectCodeLinkCoverage` 에 infra 제외 옵션 추가

**파일**: `packages/definition-catalog/src/code-references.ts`

현재 `IGNORED_DIRS = {node_modules, dist, .git, .next, .turbo, coverage}` 와 `TEST_FILE_RE` 만 있고 "harness 전용 패키지" 제외 로직이 없다. 다음 중 하나를 권장한다.

- **옵션 A (권장, breaking 없음)**: `CodeLinkCoverageOptions` 에 `excludePackages?: readonly string[]` 추가. `def doctor` 와 `def code-link-gaps` 호출 시 기본값으로 `["simulation-tests","facet-tests","viteplus-sdk-smoke","bench"]` 주입. (packages 가 늘어나도 옵션 확장만으로 대응)
- **옵션 B (minimum)**: `IGNORED_DIRS` 에 `synced` 와 `__mocks__` 를 추가 + harness 패키지 4 종을 `scope` 블랙리스트로 `def doctor` 전용 default 로 내장.
- **옵션 C (메타데이터 기반, 장기)**: 각 패키지 `package.json` 에 `"qaSdk": {"kind": "test-harness"}` 필드 선언, walker 가 이를 읽어 skip. 장점: 신규 harness 추가 시 자동 인식.

### 제안 2 — Category C 어노테이션 추가 캠페인

- 대상: 위 §C 176 건
- 우선순위: P0(public SDK) → P1(meta-semantic core) → P2(service layer) → P3(demo/derived)
- 작업 단위: 패키지별 PR 1건, 평균 5~20 건 `@def.boundary <spec-id>` 주석 1 줄 추가.
- 선행 조건: 각 파일이 가리킬 스펙 id 사전 조사 (`convergence/*` 는 `docs/specs/convergence-system/` 존재, `decision-flow/*` 는 `docs/specs/decision-flow/` 존재, `event-catalog/*` 는 `docs/specs/apm-system/apm-schema-system/` 존재).

### 제안 3 — Category D follow-up 리뷰

- 28 건을 위에 열거한 "흡수 후보" / "독립 스펙 후보" / "demo" 로 재분류하는 후속 리뷰를 별도 세션에서 실행.
- 산출: 각 파일의 target spec-id (기존 또는 신규) 결정표.

### 제안 4 — doctor 출력 개선

- `def doctor` 의 coverage 섹션에 "raw / adjusted" 두 수치를 동시에 출력하고, A 로 제외된 파일 수도 표기하여 오해를 방지한다.
- Summary 메시지:
  ```

  raw:             81.3% (1340/1649) — includes simulation-tests/synced/, mocks, viteplus-sdk-smoke, bench
  ```
