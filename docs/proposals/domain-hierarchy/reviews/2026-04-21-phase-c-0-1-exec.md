# Phase C-0/C-1 Execution — Aspect Schema Hierarchy 인프라 도입

## 목적 ^purpose

[aspect-schema-hierarchy RFC](../../aspect-schema-hierarchy/) 의 **Phase C-0 (schema + populate)** 와 **Phase C-1 (validator bridge + insert-on-discovery)** 을 비파괴적으로 실행한 결과를 기록한다. 런타임 상수 `ASPECT_PARENTS` 를 DB 의 1 st-class metadata 로 승격하되, catalog 패키지의 순수성은 그대로 유지한다. Phase C-2 (rollup API) 는 실증 수요(≥3 회) 도달 시 착수하도록 보류.

## C-1 bridge 구조

### 설계 원칙 — catalog 패키지 순수성

RFC 00-design §R3 대응. `definition-catalog` 은 DB 의존 없는 순수 라이브러리로 유지:

- `deriveAspectParent(aspect)` 는 그대로 (runtime `ASPECT_PARENTS` map 만 사용)
- `ASPECT_PARENTS` map 은 여전히 build-time SSOT (Phase C-3 deprecation 후에도 fallback 경로로 영속)
- DB 의존은 `definition-service` 패키지 내부에서만 존재

### Bridge 구현

`packages/definition-service/src/core/aspect-registry.ts` (신규)

```ts
export function createAspectRegistry(db?: DefinitionServiceDatabase): AspectRegistry {
  return {
    getAspectParent(childId): string | null {
      if (!db) return deriveAspectParent(childId);
      try {
        const row = db.select().from(aspectParents).where(eq(aspectParents.childId, childId)).get();
        if (row) return row.parentId;
      } catch (err) {
        logger.warn({ err, childId }, "aspect_parents 조회 실패 — runtime map fallback 적용");
      }
      return deriveAspectParent(childId);  // Fallback 경로
    },
    getChildrenOf(parentId): string[] { /* DB → runtime map fallback */ },
  };
}
```

- **Fail-open**: DB 미전달 / row 없음 / 조회 예외 → runtime map fallback. 빈 테이블도 그대로 통과.
- **DB 미전달 모드**: `createAspectRegistry()` 는 pure fallback 모드로 동작 — 테스트 및 catalog-only 호출자 재사용 가능.

### 테스트

`packages/definition-service/src/core/aspect-registry.test.ts` — 6 케이스:
- DB 경로: `getAspectParent` 전 쌍 매치, `getChildrenOf` 모든 자식 부모 일치
- Fallback 경로: 빈 DB → runtime map, 최상위/미등록 → null
- DB 미전달: runtime map 과 동치

## Insert-on-discovery 구현

### NestJS 경로 — `sync.service.ts`

- `onModuleInit()` — 부팅 직후 `syncAspectParents(db)` 1 회 호출 (migration 직후 populate 보장)
- `run()` — POST /sync 시마다 self-heal 실행 (PR 로 신규 자식 aspect 가 들어오면 그 다음 sync 시 자동 upsert)
- orphan drift (DB 에만 존재) 는 warning 로그만 — 수동 검토로 우회, 자동 삭제 금지

### Helper — `sync/aspect-parents-sync.ts`

```
export function syncAspectParents(db): AspectParentSyncReport {
  // 1. map → DB: 없으면 INSERT, parent 다르면 UPDATE, 같으면 unchanged
  // 2. DB-only orphan 은 driftOrphans 리스트로 보고
  return { inserted, updated, unchanged, driftOrphans };
}
```

- **Idempotent**: 같은 입력 반복 호출 시 inserted=0, unchanged=19 (테스트로 증명)
- Drift 치유 범위: map 기준으로만 INSERT/UPDATE. 삭제는 금지 (명시 migration 필요)

### CLI 경로 — `sync-local-db.ts`

CLI 는 `resetTables()` + 단일 트랜잭션 재적재 구조라 drift 가 누적되지 않는다. 그대로 populate 는 transaction 내부에서 `tx.insert(aspectParents).values(aspectRows).run()` 로 19 row 재삽입.

### 테스트

`packages/definition-service/src/sync/aspect-parents-sync.test.ts` — 5 케이스:
- 최초 호출 시 모든 쌍 INSERT
- 재호출 idempotent (inserted=0, unchanged 일치)
- stale parent_id → UPDATE
- DB-only orphan → driftOrphans 보고만
- description 컬럼 `DEFINITION_TAXONOMY` 에서 보강

## 미완 C-2 준비

RFC 01-migration §"Phase C-2" 기준 실증 수요 (rollup 요구 ≥ 3) 미달 — 1/3 만 관찰 (`def audit --rollup-aspect` 요청 1 건). 따라서 본 session 은 **C-2 진입 보류**.

### C-2 착수 조건

- rollup 요구 누적 3 건 도달 또는 DKG `getAspectFamily` 브릿지가 정식 consumer 확보
- 착수 시 예상 공수: 1-2 일 (RFC 01-migration §C-2 spec 그대로)

### C-2 구현 포인트

- `aspect-registry.ts` 에 `getAspectFamily(aspect): readonly string[]` 추가 — 기존 bridge 에 method 1 개 증분
- `packages/cli/src/commands/def.ts` 의 `cmdList` / `cmdAuditDb` 에 `--include-children` / `--rollup-aspect` 플래그 통합
- 2-level tree 전제 유지 (RFC 00-design Q5)

### C-3 착수 조건

C-2 완료 후 **1 릴리즈 cycle** 관찰 기간 경과. JSDoc `@deprecated` 표시 단계 — 실제 map 제거는 Phase C-4 또는 영구 유지 결정에 묶임.
