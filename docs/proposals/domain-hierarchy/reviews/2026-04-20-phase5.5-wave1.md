# Phase 5.5 Wave 1 — 핵심 도메인 의존 시나리오 커버리지

## 목적 ^purpose

Phase 3b에서 추가된 46건 child→parent `depends_on` 링크 중 5개 핵심 도메인(APM, DF, Gate, Ingest, Decode)에 속한 `lifecycle: approved` 자식 의존성 12건에 대해 소비자 기대 시나리오(`*.cases.md`)를 작성한다. 00-design §2.5 정책과 01-migration Phase 5.5의 첫 파도(Wave 1)로서, 향후 전체 커버리지 확장의 패턴 seed를 확립한다.

## Wave 1 범위

- **대상 도메인**: apm-system, df-system, gate-system, ingest-system, decode-system (5 core)
- **대상 링크**: Phase 3b 추가 46건 중 위 5개 도메인에 속한 `lifecycle: approved` child→parent `depends_on`
- **제외**: draft lifecycle, proposal 문서, cross-domain peer 링크
- **생성 형식**: 소비자 소유 `.cases.md` (consumer-driven, 00-design §2.5)

### 공통 구조

각 시나리오는 다음 4요소를 담는다:

1. **전제** — 부모 시스템이 제공하는 계약 상태
2. **동작** — 자식이 트리거하는 호출 경로
3. **기대** — 자식이 의존하는 결과 (계약의 본질)
4. **실패 시 수정 대상** — 1줄, 어느 부모 스펙 어디를 고쳐야 하는가

이 네 번째 필드가 Phase 5.5의 품질 게이트다. "애매한 기대"나 "공급자-소비자 공동 수정 필요"는 의미론 불명확 신호이며, 그 경우 링크 자체의 재검토를 권장한다.

## 재사용된 기존 문서

없음. 12건 모두 신규 `.cases.md` 생성.

기존 공급자 소유 `.test.md` (gate-consistency.test.md, gate-event-bus.test.md, decode-bigint.test.md)는 child의 *자체 구현*을 검증하지, 부모(gate-system/decode-system)에 대한 *소비자 기대*를 명시하지 않는다. 따라서 별도 `.cases.md`가 필요하며, 두 문서는 직교 목적을 가진다:

- `.test.md` (provider-owned): "나의 자체 스펙을 어떻게 검증하는가"
- `.cases.md` (consumer-owned): "부모에게 무엇을 기대하는가"

## 발견된 이슈

### 1. 부모가 그룹 hub에 그치면 시나리오가 boilerplate에 가까워짐

`*-group` 자식이 `system`을 의존할 때, 시스템이 "그룹 모음"에 불과하면 구체적 계약이 없어 시나리오가 *group이 expected로 내놓는 외부 contract의 정의*가 아닌, *그룹 간 조합 규칙*만 남는다. 특히 df-model-group은 model 자체가 df-system core이므로 방향 자체를 재검토해야 함 (Wave 2 사유).

### 2. `knowledge_kind: narrative` 부모/자식은 시나리오가 부자연

df-narrative-group은 narrative 서술문이 본질이라 "이 의존이 실패하면 무엇을 고치나" 질문이 부자연. narrative 증명 cluster(df-narrative-proofs) 단위로 별도 증명 문서 접근 권장.

### 3. `.test.md`와 `.cases.md`의 역할 분리 명확화 필요

Gate/Decode 도메인은 기존 provider `.test.md`가 있지만 consumer expectation을 담고 있지 않아 `.cases.md` 신규 작성이 필요했다. 이는 00-design §2.5의 구분을 실증하며, 다음 skill 가이드 또는 def-audit 리포트에 이 분리를 명시 권장:

- provider `.test.md`: "나의 구현이 나의 스펙을 검증"
- consumer `.cases.md`: "부모에게 나의 기대가 무엇인가"

### 4. `def audit --coverage` 미구현

01-migration Phase 5.5의 `qa-sdk def audit --coverage` 플래그는 아직 구현되지 않았다. Wave 1은 수동 인벤토리 기반으로 진행했다. Phase 6(CLI 확장) 또는 별도 단계에서 다음 기능이 추가되면 Wave 2+는 자동화 가능:

- `def audit --coverage` — child→parent `depends_on` 전수 스캔 + `.cases.md` / `.test.md` 매칭 여부 리포트
- `dependency-without-scenario` warning — approved + core domain 조건에서 커버리지 결손 경고

## 다음 단계 (Wave 2 제안)

1. **df-model-group / df-narrative-group 링크 재검토** — Wave 1에서 보류된 2건. df-system의 내부 구성 재검토 필요 (메타 관계).
2. **Non-core domain 확장** — browser, dkg, pipeline, query, registry, viz, wi 등 9~10개 도메인에 대해 Wave 1 패턴 재적용.
3. **CLI 지원** — `def audit --coverage` + `dependency-without-scenario` 도입 (Phase 6 or 5.5b).
4. **skill 가이드 확장** — `def-audit` / `doc-lifecycle` skill 에 `.cases.md` 생성 플로우 추가.
