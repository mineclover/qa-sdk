## 설계 선택 — Approach C (기존 layout 확장)

### 고려한 대안

- **A) 단일 `system-root-layout.md`**: 모든 도메인 루트를 한 파일로 모음. 기존 `system-root` 레벨과 중복되며 소프트 15-ref 예산을 초과할 가능성 큼.
- **B) 2단 tiered**: `system-root` + 도메인별 `<domain>-domain-layout`. 새 파일 다수 필요 (df/wi/gate/decision 등). 이미 `system-design-tools` / `system-infra` / `system-libraries` / `system-frontend` / `system-support` 가 이 역할을 하고 있어 중복.
- **C) 기존 layout 확장 (선택)**: 5개 기존 sub-layout에 orphan을 수용. 새 파일 0개. 원형 유지.

### C 선택 근거

1. `system-root` → 5개 서브 layout 구조가 이미 "도메인 루트 → 도메인 구성원" 계층을 구현하고 있다.
2. 21개 orphan 중 대부분이 주제상 기존 sub-layout 카테고리에 자연스럽게 들어맞는다 (ingest/gate/df/viz/permission 도메인).
3. 새 파일 생성 없이 `links.refs` 배열만 확장 → 가장 최소 변화.
4. 예산: `system-support`만 16→19로 ~15 soft limit을 소폭 초과하나 단일 flat 목록으로 가독성 유지 가능. 향후 Phase 5+에서 "validation" 또는 "shared-utility"만 별도 서브 layout으로 분리할 여지 남김.
