### 진단: pre-existing `depends_on` 역방향 안티패턴

검증 실패 근본 원인은 **`*-system` 부모 문서들이 자식 서브시스템을 `depends_on`으로 역참조**하고 있는 기존 구조에 있다. 예시:

```yaml
# docs/specs/apm-system/apm-system.md (부모)
links:
  - target: apm-codegen-system    # ← 자식을 depends_on으로 참조 (의미 왜곡)
    type: depends_on
  - target: apm-schema-system
    type: depends_on
  - target: apm-runtime-system
    type: depends_on
```

의미론: "apm-system이 apm-codegen-system에 의존한다"는 뜻이지만, 실제 관계는 "apm-codegen은 apm의 서브시스템" 이므로 `contains`가 맞다. 현행 구조에서 자식에 `depends_on: apm-system` 링크를 추가하면 **양방향 depends_on 사이클**이 형성된다:

```
apm-codegen-system → apm-system → apm-codegen-system  (cyclic-types: depends_on, refines, implements)
```

validator의 `circular-ref` 탐지(validate.ts:116–131)는 이 패턴을 에러로 보고한다.

## 근본 원인 심층 분석

### 왜 부모가 자식에 `depends_on`을 걸었는가?

Phase 0 설계 이전, `contains`는 "패키지 소유"의 무거운 의미로 해석되어 회피되었다(`00-design.md §1.4`). 그 공백을 현행 스펙 저자들이 `depends_on`으로 메웠고, 방향을 "parent depends on its children (for aggregation)" 로 해석한 케이스가 누적되었다.

이 해석은 의존성 의미론과 충돌한다:
- 의존성 표기: **A가 B에 기대한다 (A → B)**
- 소속 표기: **B가 A의 일부이다 (B ⊂ A)**

부모→자식 `depends_on`은 두 관계가 섞인 형태이며, Phase 3 파생 로직에는 해석 불가능한 잡음이다.

### 수정 방향

**제안: 부모→자식 링크를 `depends_on` → `contains`로 변환**.

검증 규칙상 `contains`는 cycle 탐지 대상이 아니므로(cyclicTypes = {depends_on, implements, refines}), 자식→부모 `depends_on`과 부모→자식 `contains`는 공존 가능하다. 이것이 Phase 3 정상 실행 전제.

수정 대상 `*-system` 문서 (Category A/B 합쳐 **27개 부모-자식 쌍의 부모들**):
- apm-system, browser-system, df-system, gate-system, index-meta-system, ingest-system, motion-workspace-system, permission-system, query-system, scope-nesting-system, viz-system, wi-system, decode-system, dkg-system

각 부모의 frontmatter에서 자식 대상 `type: depends_on` → `type: contains` 치환이 필요. 예:

```diff
  links:
-   - target: apm-codegen-system
-     type: depends_on
+   - target: apm-codegen-system
+     type: contains
```

이 수정 후 Phase 3 47건 재적용 시도해야 한다.
