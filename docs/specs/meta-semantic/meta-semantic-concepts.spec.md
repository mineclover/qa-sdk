# 핵심 개념

## 목적 ^purpose

데이터와 로직 추적의 기초 표준이 되는 7가지 원자 개념을 정의한다.
각 개념은 의존 순서로 쌓이며, 하위 개념 없이 상위 개념이 성립하지 않는다.

**이 표준의 범위:** 데이터의 흐름과 로직의 구조를 동시에 추적한다.
5원 분리는 데이터의 역할을, 바운더리 이상은 로직의 구조를 다루며,
Spacetime UID에서 데이터와 로직이 하나의 주소 체계로 합류한다.

## 구성 ^overview

의존 순서:

1. **5원 분리** — 데이터의 5가지 역할을 분리하는 설계 규칙 (토대)
2. **바운더리** — 5원 중 일부가 존재하는 검증 가능한 기능 단위. 모듈을 정의하는 것
3. **계약 하향** — 바운더리 간 상호 무지, 자기 계약 명확
4. **Semantic Folding** — 코드에서 바운더리를 찾는 메커니즘
5. **검증 단위** — Folding이 산출하는 것: 독립 테스트 가능한 함수
6. **분기 경로** — 검증 단위 내의 경우의 수를 세는 방법
7. **Spacetime UID** — 분기 경로에 시간을 결합한 주소

## 1. 5원 분리 (Five-Role Separation)

**데이터의 5가지 역할은 반드시 분리한다.**

| 역할 | 한 줄 정의 | 판별 질문 |
|------|-----------|----------|
| **생산** | 데이터가 입력되고 생성되는 시작점 | "이 코드가 새 데이터를 만드는가?" |
| **소비** | 특정 모듈 컨텍스트에서 데이터를 사용하는 것. 소멸이 아님 | "이 코드가 기존 데이터를 읽거나 표시하는가?" |
| **정의** | 기능적 필요에 의한 스펙 정의. 스키마 | "이 코드가 데이터의 형태를 선언하는가?" |
| **관리** | 정합성 보장, 트랜잭션 보장. 계약은 여기에 해당 | "이 코드가 데이터의 유효성을 보장하는가?" |
| **저장** | 실제 저장 방식. 고유 식별자 부여 체계가 핵심 | "이 코드가 데이터를 영속화하거나 UID를 부여하는가?" |

### 이것이다 / 이것이 아니다

| 코드 예시 | 역할 | 아닌 것 |
|----------|------|---------|
| `return new User(name, age)` | 생산 | 소비가 아님 (만듦) |
| `<div>{user.name}</div>` | 소비 | 생산이 아님 (표시만) |
| `interface User { name: string }` | 정의 | 관리가 아님 (선언만, 강제 안 함) |
| `if (!isValid(data)) throw` | 관리 | 생산이 아님 (판단만) |
| `await db.insert(user)` | 저장 | 생산이 아님 (영속화만) |
| `const result = transform(a, b)` | 생산 (변형 결과) | 이동이 아님 (새 데이터 생성) |
| `service.process(data)` | 해당 없음 (이동) | 이동은 모듈 관계에 내재, 별도 역할 아님 |

### 각 역할은 독립적으로 존재할 수 있다

하나의 바운더리에 5원이 전부 있을 필요 없다.
정의만 있는 바운더리(타입 선언), 소비만 있는 바운더리(UI 컴포넌트),
생산만 있는 바운더리(입력 핸들러)가 각각 별도로 존재할 수 있다.

### 왜 분리하는가

좌표를 적절히 나누면서 일관성을 유지하기 위한 규칙이다.
5개 역할이 뒤섞이면 데이터의 정체성이 모호해지고 좌표화가 불가능해진다.

**판별 기준:**
어떤 코드가 데이터를 다룰 때, "이 코드는 5원 중 어느 역할을 수행하는가?"를 물으면
그 코드의 책임이 명확해진다. 하나의 코드가 여러 역할을 수행하면 분리 신호다.

### 소비의 정확한 의미

소비는 **소멸이 아니다.** 특정 모듈 컨텍스트에서 데이터를 **사용**하는 것이다.
소비 후에도 데이터는 존재한다. UI에 표시, 조건 판단에 사용, 로그에 기록 — 모두 소비.

### 데이터 계보: 이동과 변형

**이동은 별도 역할이 아니다.** 모듈의 호출, 사용, 의존성 주입에서 자연히 발생한다.
이동은 모듈 관계(relations)에 내재된 것이지 데이터의 독립적 역할이 아니다.

**추적해야 할 것은 변형이다.**

변형은 이동 전에 발생하기도 하고, 입력의 조합으로 발생하기도 한다.
변형의 결과는 두 갈래:
- **새 데이터의 생성** — 기존 데이터에서 완전히 새로운 데이터가 만들어짐
- **다른 데이터로의 변환** — 기존 데이터가 계산을 거쳐 형태가 바뀜

**변형 후 저장으로 표현한다.**
변형된 결과는 저장(UID 부여)됨으로써 계보가 추적된다.

| 현상 | 5원으로의 표현 |
|------|-------------|
| A→B 이동 | 모듈 관계에 내재 (별도 역할 불필요) |
| A→f(A)→B 변형 | B는 새 **생산** + **저장**(UID 부여). A→B 관계는 UID 체인 |
| A+C→D 조합 | D는 새 **생산** + **저장**. A,C→D 관계는 UID 체인 |

**결론: 5원을 유지한다.**
이동은 모듈 관계에 내재, 변형은 생산+저장의 조합으로 표현.
데이터 계보는 저장의 UID 체인(Spacetime UID)이 추적한다.

## 2. 바운더리 (Boundary)

**5원 중 일부가 존재하는 검증 가능한 기능 단위. 이것이 모듈을 정의한다.**

### "검증 가능"의 기준

바운더리가 되려면 다음 중 하나 이상을 만족해야 한다:

| 검증 유형 | 예시 | 확인 방법 |
|----------|------|----------|
| **실행 검증** | 함수를 호출하고 결과를 확인 | 단위 테스트 |
| **타입 검증** | 스키마가 컴파일 타임에 통과 | 타입 체커 |
| **계약 검증** | 입출력이 명세와 일치 | 계약 테스트 |
| **정합성 검증** | 데이터가 규칙을 만족 | 검증 함수 |

"검증 가능"이란 **결과를 기계적으로 판정할 수 있는가**이다.
코드 리뷰로만 확인 가능한 것은 검증이 아니다.

### 바운더리 예시

```
순수 함수 (leaf):
  정의 ✓  — 입력/출력 타입이 있다
  생산 ✓  — 결과를 생성한다
  소비 ✓  — 입력을 사용한다
  관리 ✗  — 정합성 보장은 상위가 담당
  저장 ✗  — UID 부여는 상위/외부가 담당
  검증: 단위 테스트로 입출력 확인 → 유효한 바운더리

타입 선언 (leaf):
  정의 ✓  — 스키마를 선언한다
  나머지 ✗
  검증: 컴파일 타임 타입 체크 → 유효한 바운더리

서비스 클래스 (module):
  정의 ✓  관리 ✓  생산 ✓  소비 ✓  저장 ✓
  검증: 통합 테스트로 계약 확인 → 유효한 바운더리
```

### 이것은 바운더리가 아니다

| 코드 | 이유 |
|------|------|
| 내부 헬퍼 함수 (private, 외부 계약 없음) | 독립 검증 불가 — 호출자에 종속 |
| 주석, 문서 | 5원 중 어느 것도 존재하지 않음 |
| 설정 파일 (.env, config.json) | 데이터 역할을 수행하지 않음 — 환경 파라미터 |

### 모듈과의 관계

바운더리 = 모듈이다. 모듈은 "코드의 구조적 단위"가 아니라
"5원 중 일부가 존재하는 검증 가능한 기능 단위"에 의해 정의된다.
어떤 5원이 존재하느냐에 따라 모듈의 성격(leaf/module/group)이 달라진다.

## 3. 계약 하향 (Contract Descent)

**계약은 상위에서 하위로 내려가고, 트랜잭션은 하위에서 상위로 올라간다.**

### 상위-하위 관계

```
상위 바운더리 (관리자)
  │
  ├── 계약 ↓ (스키마, 검증 규칙)
  │
  ├── 하위 바운더리 A ── 계약 범위 내에서 생산
  │     └── 트랜잭션 ↑
  │
  └── 하위 바운더리 B ── 계약 범위 내에서 소비
        └── 변경 요청 ↑
```

### 동등 수준(peer) 관계

상위-하위만 있는 것이 아니다. 동등 수준의 바운더리도 존재한다.

```
바운더리 A ←── API 계약 ──→ 바운더리 B
  │                           │
  └── 자기가 소비할            └── 자기가 소비할
      B의 API만 앎                 A의 API만 앎
```

동등 수준에서도 원칙은 동일: **자기가 소비할 계약만 명확히 안다.**
공유 데이터가 있으면 공통 상위 바운더리가 관리를 담당한다.

### 핵심 원칙: 상호 무지, 자기 계약 명확

상위도 하위의 세부를 모르고, **하위도 상위의 세부를 모른다.**
동등 수준의 peer도 서로의 세부를 모른다.
각 바운더리는 자신이 소비할 내용 외에는 이해하지 않아도 된다.
대신, **자신이 소비해야 할 데이터, 계약, 트랜잭션은 명확히 알아야 한다.**

### 4가지 규칙

1. **상위는 하위의 세부를 모른다.** 계약만 내려주고 결과만 받는다.
2. **하위도 상위의 세부를 모른다.** 자기가 소비할 계약/데이터/트랜잭션만 안다.
3. **자기가 소비할 것은 명확히 안다.** 모르는 건 자유이지만 아는 건 의무다.
4. **공유 데이터는 상위가 관리.** n개 모듈이 같은 데이터를 쓰면 상위 계층에 관리 위임.

### 왜 이 구조인가

각 바운더리가 자기 계약만 명확히 알면 독립적으로 검증 가능하다.
상대방의 내부를 몰라도 되므로 교체, 이동, 테스트가 자유롭다.

## 4. Semantic Folding

**코드를 접고 펼쳐서 바운더리를 찾는 메커니즘.**

Folding은 시각화가 아니다. "무엇을 좌표화할 것인가"를 결정하는 사전 단계다.
모든 코드에 좌표를 부여하면 주소 공간이 폭발한다.
접어서 바운더리를 찾고, 그 바운더리 내의 검증 단위만 좌표화한다.

### 3단계

| 레벨 | 접었을 때 | 판단 |
|------|----------|------|
| L0 System | 시스템 간 데이터 흐름만 | "이 패키지는 하나의 바운더리인가?" |
| L1 Module | 모듈 간 계약만 | "이 클래스는 5원 중 일부를 가진 검증 가능 단위인가?" |
| L2 Leaf | 함수 단위 로직 | "이 함수는 독립 검증 가능한가?" |

### Folding의 산출물

검증 단위 목록 — 좌표를 부여할 대상.

### Folding은 시각화가 아닌 이유

시각화는 Folding의 부산물이다. 접기/펼치기가 자연스럽게 줌 레벨을 만들지만,
Folding의 본질적 목적은 **좌표화 대상 선별**이다.

## 5. 검증 단위 (Verification Unit)

**Semantic Folding이 식별한, 독립적으로 테스트 가능한 함수.**

검증 단위는 좌표를 부여할 가치가 있는 코드의 최소 단위다.

### 검증 가능 기준

- 명확한 입력/출력 타입이 있다
- 부수효과가 식별 가능하다 (또는 없다)
- 다른 함수와 독립적으로 테스트할 수 있다

### 이것이다 / 이것이 아니다

| 코드 | 검증 단위? | 이유 |
|------|-----------|------|
| `processOrder(order: Order): Receipt` | ✓ | 명확한 I/O, 독립 테스트 가능 |
| `validate(data: Input): boolean` | ✓ | 명확한 I/O |
| `UserComponent({ user }: Props)` | ✓ | 컴포넌트 = 입력→렌더 결과 |
| `private helper()` | ✗ | 외부 계약 없음, 독립 테스트 불가 |
| `get name() { return this._name }` | ✗ | 로직 없음 |
| `if (x == null) return` | ✗ | 분기이지만 검증 단위는 아님 |

### LLM의 역할

검증 단위의 식별은 LLM이 수행한다.
"이 함수는 독립 테스트 가능한가?"는 의미적 판단이지 구문적 사실이 아니다.
AST 파서는 함수 시그니처, 타입 정보 등 구조적 사실만 제공한다.

## 6. 분기 경로 (Branch Path)

**검증 단위 내에서, 도달 가능한 분기점을 따라가며 경우의 수를 세는 방법.**

전체 변수의 전곱(N×M)이 아니라, **이벤트별 도달 가능한 경로의 합**이다.

### 곱과 합의 규칙

```
전곱:  A(3) × B(4) × C(2) = 24    ← 도달 불가능한 조합 포함
경로:  A(3)→B(4) = 12,  A(3)→C(2) = 6  → 합: 18  ← 도달 가능한 것만
```

- 분기점 A에서 다음에 **순차 도달**하는 분기점 B → A × B (곱)
- A에서 도달하는 B와 C가 **독립** → (A×B) + (A×C) (합)

**"독립"의 판별:** B에서 C에 도달 불가능하고, C에서 B에 도달 불가능하면 독립.
B→C가 도달 가능하면 B와 C는 순차 관계이므로 곱.

### 의미 없는 분기 제외

| 분기 | 포함? | 이유 |
|------|-------|------|
| `if (type === 'card')` | ✓ | 비즈니스 로직 분기 |
| `switch (status)` | ✓ | 상태 기반 분기 |
| `if (x == null)` | ✗ | 방어적 체크 |
| `try/catch` | ✗ | 에러 처리 |
| `if (DEBUG)` | ✗ | 개발 도구 |

### WeightedIndex와의 관계

각 독립 경로를 별도 WeightedIndex 인스턴스로 인코딩하고,
주소 범위를 연접(concatenation)한다.

## 7. Spacetime UID

**분기 경로 주소에 시간 축(tx_seq)을 결합한 시공간 식별자.**

```
Spacetime UID = (함수, 경로 주소, 실행 순번)
                  what      where       when
```

- **함수 (what):** 어떤 검증 단위인가
- **경로 주소 (where):** 검증 단위 내 어떤 분기 조합인가
- **실행 순번 (when):** 그 경로가 몇 번째 실행되었는가

### 불변성

기존 주소는 영원히 바뀌지 않는다. 새 실행은 새 tx_seq, 새 분기는 새 segment.
이것이 데이터 5원 분리 중 **저장**의 핵심 — 고유 식별자 부여 체계.

### 데이터 계보 추적

변형(A→f(A)→B)이 발생하면 결과 B는 새 생산+저장(새 UID)이다.
A의 UID와 B의 UID가 체인으로 연결되어 계보가 추적된다.

```
데이터 A: intent:v1:1:0:41  (processOrder, normal×card, 41번째)
  ↓ 변형 (할인 계산)
데이터 B: intent:v1:2:3:1   (calcDiscount, express×percent, 1번째)
  계보: A.uid → B.uid (변형 관계)
```

이동은 모듈 관계에 내재되어 별도 추적 불필요.
변형만 UID 체인으로 추적하면 데이터 계보가 완성된다.

### 저장 역할과의 관계

Spacetime UID는 5원 분리의 "저장" 역할을 실현하는 메커니즘이다.
좌표를 적절히 나누면서 일관성을 유지하는 규칙이 곧 UID 부여 체계다.

## 개념 의존 그래프

```
① 5원 분리
   └── ② 바운더리 ("5원 중 일부가 존재하는 검증 가능 기능 단위가 모듈이다")
        └── ③ 계약 하향 ("상호 무지, 자기 계약 명확")
             └── ④ Semantic Folding ("코드에서 바운더리를 찾는 방법")
                  └── ⑤ 검증 단위 ("Folding이 산출하는 것")
                       └── ⑥ 분기 경로 ("검증 단위 내 경우의 수")
                            └── ⑦ Spacetime UID ("경로 + 시간 = 주소")
```

아래에서 위로: 5원 분리가 없으면 바운더리를 정의할 수 없고,
바운더리가 없으면 Folding할 대상이 없고,
Folding이 없으면 검증 단위를 식별할 수 없고,
검증 단위가 없으면 분기 경로를 셀 수 없고,
분기 경로가 없으면 UID를 부여할 수 없다.

## qa-sdk 기존 개념과의 대응

| meta-semantic 개념 | qa-sdk 기존 개념 | 관계 |
|---|---|---|
| 5원 분리 | — | 신규. qa-sdk에는 없던 데이터 역할 분리 규칙 |
| 바운더리 | DefLevel (group/module/leaf) | 바운더리가 DefLevel을 결정 |
| 계약 하향 | contains 링크 + concern 전파 | 방향이 같음 (상위→하위) |
| Semantic Folding | assembleFeature() 접기/펼치기 | 문서 조립의 코드 확장 |
| 검증 단위 | DefinitionEntry (leaf) | 좌표 부여 대상의 최소 단위 |
| 분기 경로 | PrefixDef.dims (축 조합) | 전곱→경로 모델로 확장 |
| Spacetime UID | SemanticAddress (schema:version:index) | 동일 직렬화 체계, 다른 차원 구성 |
