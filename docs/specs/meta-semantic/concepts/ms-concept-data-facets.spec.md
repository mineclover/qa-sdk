# 데이터 패싯 (Data Facets)

## 목적 ^purpose

데이터의 흐름을 검증 가능한 단위로 쪼개는 설계 규칙을 정의한다.
현재 식별된 역할은 5가지(생산·소비·정의·관리·저장)이지만,
독립적인 역할이 더 발견되면 확장한다. **5개로 고정이 아니다.**

핵심은 "데이터의 흐름을 검증 가능한 독립 단위로 쪼갠다"이며,
이 규칙 없이는 바운더리, 계약 하향, 좌표화 등 상위 개념이 성립하지 않는다.

### 확장 기준

새 역할을 추가하려면:
- 기존 역할 중 어느 것으로도 환원되지 않는 독립적 행위인가?
- 그 행위를 분리하면 검증이 더 쉬워지는가?
- 분리하지 않으면 다른 역할과 뒤섞여 좌표화가 모호해지는가?

3가지 모두 충족하면 새 역할로 추가한다.

---

## 5가지 역할

| 역할 | 한 줄 정의 | 판별 질문 |
|------|-----------|----------|
| **생산** | 데이터가 입력되고 생성되는 시작점 | "이 코드가 새 데이터를 만드는가?" |
| **소비** | 특정 모듈 컨텍스트에서 데이터를 사용하는 것. 소멸이 아님 | "이 코드가 기존 데이터를 읽거나 표시하는가?" |
| **정의** | 기능적 필요에 의한 스펙 정의. 스키마 | "이 코드가 데이터의 형태를 선언하는가?" |
| **관리** | 정합성 보장, 트랜잭션 보장. 계약은 여기에 해당 | "이 코드가 데이터의 유효성을 보장하는가?" |
| **저장** | 실제 저장 방식. 고유 식별자 부여 체계가 핵심 | "이 코드가 데이터를 영속화하거나 UID를 부여하는가?" |

## 이것이다 / 이것이 아니다

| 코드 예시 | 역할 | 아닌 것 |
|----------|------|---------|
| `return new User(name, age)` | 생산 | 소비가 아님 (만듦) |
| `<div>{user.name}</div>` | 소비 | 생산이 아님 (표시만) |
| `interface User { name: string }` | 정의 | 관리가 아님 (선언만, 강제 안 함) |
| `if (!isValid(data)) throw` | 관리 | 생산이 아님 (판단만) |
| `await db.insert(user)` | 저장 | 생산이 아님 (영속화만) |
| `const result = transform(a, b)` | 생산 (변형 결과) | 이동이 아님 (새 데이터 생성) |
| `service.process(data)` | 해당 없음 (이동) | 이동은 모듈 관계에 내재, 별도 역할 아님 |

## 각 역할은 독립적으로 존재할 수 있다

하나의 바운더리에 패싯이 전부 있을 필요 없다.
정의만 있는 바운더리(타입 선언), 소비만 있는 바운더리(UI 컴포넌트),
생산만 있는 바운더리(입력 핸들러)가 각각 별도로 존재할 수 있다.

## 왜 분리하는가

좌표를 적절히 나누면서 일관성을 유지하기 위한 규칙이다.
5개 역할이 뒤섞이면 데이터의 정체성이 모호해지고 좌표화가 불가능해진다.

**판별 기준:**
어떤 코드가 데이터를 다룰 때, "이 코드는 패싯 중 어느 역할을 수행하는가?"를 물으면
그 코드의 책임이 명확해진다. 하나의 코드가 여러 역할을 수행하면 분리 신호다.

## 소비의 정확한 의미

소비는 **소멸이 아니다.** 특정 모듈 컨텍스트에서 데이터를 **사용**하는 것이다.
소비 후에도 데이터는 존재한다. UI에 표시, 조건 판단에 사용, 로그에 기록 — 모두 소비.

## 데이터 계보: 이동과 변형

**이동은 별도 역할이 아니다.** 모듈의 호출, 사용, 의존성 주입에서 자연히 발생한다.
이동은 모듈 관계(relations)에 내재된 것이지 데이터의 독립적 역할이 아니다.

**추적해야 할 것은 변형이다.**

변형은 이동 전에 발생하기도 하고, 입력의 조합으로 발생하기도 한다.
변형의 결과는 두 갈래:
- **새 데이터의 생성** — 기존 데이터에서 완전히 새로운 데이터가 만들어짐
- **다른 데이터로의 변환** — 기존 데이터가 계산을 거쳐 형태가 바뀜

**변형 후 저장으로 표현한다.**
변형된 결과는 저장(UID 부여)됨으로써 계보가 추적된다.

| 현상 | 패싯으로의 표현 |
|------|-------------|
| A→B 이동 | 모듈 관계에 내재 (별도 역할 불필요) |
| A→f(A)→B 변형 | B는 새 **생산** + **저장**(UID 부여). A→B 관계는 UID 체인 |
| A+C→D 조합 | D는 새 **생산** + **저장**. A,C→D 관계는 UID 체인 |

**결론: 현재 패싯을 유지한다.**
이동은 모듈 관계에 내재, 변형은 생산+저장의 조합으로 표현.
데이터 계보는 저장의 UID 체인(Spacetime UID)이 추적한다.
