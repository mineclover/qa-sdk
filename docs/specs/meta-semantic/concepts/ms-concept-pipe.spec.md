# 파이프 (Pipe)

## 목적 ^purpose

**이벤트에 의해 트리거되는 패싯의 실행 묶음**을 정의한다.
이벤트가 데이터를 생산하는 포인트이고, 파이프가 그 데이터를 처리하는 실행 단위다.
파이프의 결과가 새 이벤트를 생산할 수 있어 체인이 형성된다.

**비즈니스 로직 = 이벤트에 의해 트리거되는 파이프들의 집합.**

---

## 이벤트 → 파이프 → 이벤트 (실행 사이클)

이벤트가 파이프에 데이터를 생산하는 포인트다.

```
이벤트 발생 (데이터 생산 포인트)
  → 파이프 트리거
    → 패싯 단계 순차 수행 (소비→관리→생산→저장)
      → 새 데이터 생산 → 새 이벤트 가능 → 후속 파이프 트리거...
```

**이벤트는 qa-sdk의 EventRecord와 동일한 것이다.**
meta-semantic에서 이벤트는 새 포맷이 아니라 기존 EventRecord에
"패싯의 생산 시작점이자 파이프의 트리거"라는 의미를 부여한 것이다.

| 개념 | 의미 |
|------|------|
| 이벤트 | 데이터가 생산되는 포인트. 파이프를 트리거함 |
| 파이프 | 트리거된 이벤트를 처리하는 패싯의 실행 순서 |
| 후속 이벤트 | 파이프 결과로 생산된 새 데이터. 다음 파이프를 트리거할 수 있음 |

**비즈니스 로직 = 이벤트에 의해 트리거되는 파이프들의 집합.**
파이프가 새 이벤트를 생산하면 또 다른 파이프가 트리거되어 체인을 형성한다.

> 아키텍처 패턴: Pipes and Filters (EIP) + Event-Driven Architecture
> 이벤트 포맷: qa-sdk EventRecord (CloudEvents 유사 구조)

---

## 개념 단위 vs 실행 단위

```
개념 단위 (바운더리 = leaf/module):
  "무엇이 존재하는가" — 구조적 정의
  패싯 중 일부가 존재하는 검증 가능 기능 단위

실행 단위 (파이프):
  "무엇이 함께 실행되는가" — 행위적 정의
  개념 단위들이 확정적으로(또는 조건부로) 실행되는 묶음
```

**파이프가 없으면:** 개별 패싯은 정의되어 있지만, 실제로 어떻게 결합되어 동작하는지 알 수 없다.
**파이프가 있으면:** "이 순서로, 이 조건에서, 이 개념 단위들이 실행된다"가 명시된다.

## 파이프의 정의

```
파이프 = {
  이름,
  트리거 이벤트 (어떤 이벤트가 이 파이프를 시작하는가),
  패싯 흐름 (어떤 역할이 어떤 순서로 수행되는가),
  조건 (확정적 또는 조건부 실행),
  생산 이벤트 (실행 결과로 새 이벤트를 생산하는가)
}
```

## 대표 패턴

| 파이프 이름 | 패싯 흐름 | 설명 | 예시 |
|------------|---------|------|------|
| **변환** | 소비 → 생산 | 입력을 변형하여 출력 | `transform()`, `map()` |
| **검증** | 소비 → 관리 | 데이터를 읽고 규칙 판정 | `validate()`, `guard()` |
| **수집** | 소비 → 저장 | 외부 데이터를 받아 영속화 | API fetch → DB insert |
| **검증 생성** | 소비 → 관리 → 생산 → 저장 | 검증 후 생성하여 저장 | form submit → validate → create → save |
| **완전 처리** | 정의 → 소비 → 관리 → 생산 → 저장 | 패싯 전부 순차 실행 | CRUD service 전체 흐름 |

## 파이프와 조건

파이프는 항상 무조건 실행되는 것이 아니다. 조건부 실행이 가능하다:

```
pipe "order-processing":
  소비(주문 입력)
  → 관리(재고 확인)
  → [조건: 재고 있음]
      → 생산(주문 생성) → 저장(DB 저장)
  → [조건: 재고 없음]
      → 생산(대기 알림 생성) → 저장(큐 저장)
```

조건부 분기가 있는 파이프 = **분기 경로**의 입력이 된다.
파이프 내의 조건부 분기가 곧 분기 경로의 분기점이다.

## 파이프와 다른 개념의 관계

| 개념 | 파이프와의 관계 |
|------|---------------|
| **이벤트 (EventRecord)** | 이벤트가 파이프를 트리거. 파이프 결과가 새 이벤트를 생산할 수 있음 |
| **데이터 패싯** | 파이프는 패싯의 실행 순서를 정의. 개별 패싯 정의는 leaf에 유지 |
| **바운더리** | 바운더리 = 개념 단위, 파이프 = 실행 단위. 직교 |
| **계약 하향** | 파이프 간 계약도 동일 원칙. 파이프가 소비할 계약만 앎 |
| **Semantic Folding** | 파이프도 Folding 대상. 하위 실행 단계의 패싯을 파이프의 흐름 표현으로 접음 |
| **검증 단위** | 검증 단위 ≈ 독립 테스트 가능한 파이프. 대부분의 검증 단위는 파이프 |
| **분기 경로** | 파이프 내 조건부 분기 = 분기 경로의 분기점 |
| **Spacetime UID** | 파이프 실행 인스턴스에 UID 부여 |

## 파이프가 아닌 것

| 코드 | 이유 |
|------|------|
| 타입 선언 (`interface User {}`) | 실행이 없음 — 개념 단위(정의)만 |
| 단순 getter (`get name()`) | 실행은 있지만 확정적 묶음이 아님 |
| import 문 | 이동이지 실행이 아님 |
| 설정 로딩 | 환경 파라미터이지 비즈니스 파이프가 아님 |

## Pipe Folding

파이프도 Folding의 대상이다.
접으면 파이프의 흐름 요약만 보이고, 펼치면 각 단계의 패싯이 보인다.

```
접은 상태: "입력을 검증하고 생성하여 저장한다"
펼친 상태: 소비(입력) → 관리(검증) → 생산(생성) → 저장(DB)
```

Module이 "어떤 데이터에 접근 가능한가"를 접는다면,
Pipe는 "어떤 순서로 실행되는가"를 접는다.

> Folding 상세: `ms-concept-folding` 참조

## 핵심

**이벤트가 파이프를 트리거하고, 파이프가 패싯을 실행하고, 결과가 새 이벤트를 생산한다.**

- 개별 패싯은 쪼개서 정의하되, 실행할 때는 파이프로 묶는다
- 이벤트 = 데이터 생산 포인트 = 파이프 트리거 (qa-sdk EventRecord)
- 비즈니스 로직 = 이벤트에 의해 트리거되는 파이프들의 집합
- 파이프를 Folding하면 하위 실행 흐름이 흐름 요약으로 응축된다
