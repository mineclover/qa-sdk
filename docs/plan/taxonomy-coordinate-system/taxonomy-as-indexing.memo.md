# Taxonomy Coordinate Indexing — RDF + 좌표 인덱싱 + 재귀 내포

## 문서의 성격

이 메모는 **현재 구현 설명이 아니라 목표 모델**을 적는다.

- 이미 구현된 기능 목록을 나열하는 문서가 아니다
- taxonomy 좌표계가 충분히 성숙했을 때 어떤 조회 모델을 제공해야 하는지 정의한다
- 따라서 아래 서술은 "항상 즉시 가능하다"가 아니라, **필요한 DSL 정보가 있고 도달하려는 좌표가 충분히 특정될 때 가능해야 한다**는 목표를 뜻한다

## 시스템의 목적

1. **관찰 → 영향 조회**: 어디서 어떤 진입점으로 어떤 기능을 관찰하든, 그 관찰된 기능에 영향을 끼치는 데이터 계약·상위 컨텍스트·제약조건을 조회할 수 있어야 한다.
2. **작업 → 방향별 정보 조회**: 무언가 작업하려 할 때, 작업의 방향에 따라 필요한 정보를 조회할 수 있어야 한다.

이 두 가지가 taxonomy 좌표계가 존재하는 이유다. 관찰과 작업 모두 **임의의 진입점에서 시작**하므로, 가능하다면 그래프 순회 없이 현재 위치에서 바로 관련 정보에 도달할 수 있는 구조가 필요하다. 이것이 RDF의 관계 표현에 좌표 인덱싱을 얹는 이유이고, 노드 내부가 또 다른 좌표 공간이 될 수 있어야 하는 이유다.

단, 이것은 **일반 탐색 경로를 제거하자는 뜻이 아니다**. 좌표가 충분히 특정되지 않았거나 DSL 정보가 아직 부족하면 기존의 그래프/트리 탐색 경로가 계속 필요하다. 목표는 탐색을 없애는 것이 아니라, **직접 접근 가능한 경우를 늘리는 것**이다.

### 정체성

이 시스템이 하는 일을 한 마디로: **소프트웨어 개발 거버넌스와 개발 산출물의 온톨로지화**.

온톨로지 설계가 특정 도메인의 개념·관계·제약을 형식적으로 정의하듯, 이 시스템은 소프트웨어 개발이라는 도메인에서 거버넌스(규칙, 제약, 의사결정)와 산출물(코드, 스펙, 테스트, 배포)을 좌표 기반 온톨로지로 정의한다. 그리고 그 온톨로지를 **안정적으로 운영**하고, **의미를 수렴**시키고, **관측할 수 있는 인프라**를 개발하는 것이 목표다.

### 전제 — prefix 고유성

모든 prefix는 고유해야 한다. namespace가 고유해야 하는 것과 같은 원리다 (테이블명, RDF URI 등). taxonomy든 axis든 prefix로 표현되는 이상 이 규칙을 따른다.

이 고유성을 보장하려면 URI 등록 체계가 필요하다. 구조적으로 RDF의 namespace 등록과 같은 문제를 풀게 된다.

## 핵심 정의 — RDF + 좌표 인덱싱 + 재귀 내포

한 문장으로: **RDF에 좌표로 인덱싱하겠다 + RDF를 이루는 node 자체가 또 다른 RDF를 내포할 수 있게 하겠다.**

- **좌표 인덱싱**: RDF는 URI로 노드를 식별하지만 탐색은 그래프 순회에 의존한다. 이 시스템은 axis 교차로 정수 좌표를 부여하여, 필요한 DSL과 좌표 정보가 충분할 때 직접 접근할 수 있게 한다.
- **재귀적 내포**: RDF의 node는 단일 리소스다. 이 시스템에서는 node 자체가 내부에 별도의 taxonomy(axis 교차 구조)를 가질 수 있다. 들어가면 또 다른 좌표 공간이 펼쳐진다.

이 두 가지가 RDF 위에 이 시스템이 얹는 것이다. 나머지(고유 식별, triple 관계, namespace 관리)는 RDF가 이미 풀어둔 것을 그대로 따른다.

### RDF 대응

| 이 시스템 | RDF | 관계 |
|-----------|-----|------|
| prefix (고유 식별) | namespace prefix / URI | 동일한 문제 — 리소스 고유 식별 |
| 좌표 주소 (address) | URI | 변환 관계 — URI를 정수 좌표로 인코딩 |
| link (node - linkType - node) | triple (subject - predicate - object) | 동일한 문제 — 관계 표현 |
| taxonomy | ontology / vocabulary | 동일한 문제 — 분류 체계 정의 |
| space | named graph | 동일한 문제 — 관점별 그래프 분리 |
| axis entry | named individual | 동일한 문제 — 유한 집합의 멤버 |

### 좌표 인덱싱의 귀결 — 상대 깊이

각 노드가 고유 좌표를 가지면 **특정된 진입점은 곧 표층**이 된다. 깊이는 탐색을 시작할 때 비로소 발생하고, 좌표가 충분하면 중간을 건너뛸 수 있다.

따라서:

- `contains depth ≤ 4`는 **트리 형태의 운영 제약**이지 좌표계의 본질적 한계가 아니다
- 좌표로 직접 접근 가능한 경우에는 전체 트리 깊이가 탐색 비용과 무관하다
- 깊이 제약이 필요한 경우는 좌표 없이 트리를 순회하거나, 좌표가 충분히 특정되지 않은 상태에서 전체 구조를 읽어야 하는 상황(예: 전체 조회, 시각화)에 한정된다

## 위치 기반 컨텍스트 주입

시스템 목적 두 가지를 실현하는 메커니즘이다.

좌표 인덱싱이 여기서 만드는 차이: 필요한 DSL 정보가 있고 좌표가 충분히 특정되면, 그래프 순회 없이 **좌표로 진입하는 순간 수집 시작점이 결정**된다. 재귀 내포 때문에 노드 내부 좌표 공간의 계약도 **동일한 패턴**으로 수집할 수 있다 — 외부 그래프든 내부 좌표 공간이든 수집 메커니즘이 같다.

반대로 좌표가 덜 특정되었거나 DSL 정보가 불충분하면, 여기서 말하는 수집은 일반 탐색 경로로 fallback된다.

### 목적 1 — 관찰 시 영향 조회

어떤 기능(노드 X)을 관찰할 때, X에 영향을 끼치는 것들을 자동으로 수집한다.

```
노드 X 관찰 (좌표로 직접 진입)
  │
  ├── contains 역추적 → 상위 바운더리의 데이터 계약
  ├── constrains 역추적 → X에 적용되는 제약조건
  ├── depends_on 추적 → X가 의존하는 노드의 인터페이스
  │
  └── 수집 결과 = "X에 영향을 끼치는 모든 것"
      전제가 같다면, 진입점이 어디든 같은 좌표면 같은 결과
```

### 목적 2 — 작업 시 방향별 정보 조회

노드 X에서 작업을 시작할 때, **작업 방향**에 따라 다른 정보가 필요하다.

```
노드 X에서 작업
  │
  ├── 방향: 구현 → 하위 분해 구조, 기존 구현 패턴, 테스트 계약
  ├── 방향: 리팩토링 → 의존하는 노드 목록, 영향 범위, 상위 인터페이스 계약
  ├── 방향: 확장 → 인접 taxonomy의 해석, capacity 여유, 상위 goal과의 정합
  └── 방향: 검증 → 적용되는 rule/gate, 기대 상태, 시나리오 목록
```

작업 방향이 **어떤 taxonomy를 따라 조회할 것인가**를 결정한다. 같은 노드에서 시작해도 방향이 다르면 참조하는 taxonomy가 다르고, 수집되는 정보가 다르다.

여기서도 동일하게, 이 모델은 "방향별 직통 조회가 가능해야 한다"는 목표를 뜻한다. 실제 운용에서는 방향별 direct lookup과 일반 탐색이 함께 존재할 수 있다.

### 컨텍스트 주입의 범위

주입되는 컨텍스트는 위치에 따라 달라진다:

| 위치 | 주입되는 컨텍스트 |
|------|-----------------|
| leaf 노드 | 직접 상위 module의 계약 + module이 속한 group의 계약 |
| module 노드 | 속한 group의 계약 + 인접 module의 인터페이스 |
| group 노드 | space 수준의 전역 제약 |

깊이가 아니라 **위치가 컨텍스트를 결정**한다. 같은 depth 2라도 어떤 group 아래에 있느냐에 따라 주입되는 계약이 다르다.

## 시사점

1. **contains depth 제약 재해석**: 운영 편의 가이드라인으로 유지하되, 좌표계의 구조적 한계로 취급하지 않는다
2. **탐색 모델 이중화**: 좌표 직접 접근(전제 충족 시 우선) + 트리/그래프 순회(일반 탐색) 두 모드를 명시적으로 구분
3. **컨텍스트 주입 표준화**: 특정 노드에서 작업할 때 상위 계약을 자동 수집하는 패턴을 def 하네스에 반영
