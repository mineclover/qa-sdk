# **아키텍처 설계서: 공통 예외 처리 및 에러 응답 규약**

본 문서는 모듈러 모놀리스 시스템 내의 모든 도메인이 일관된 방식으로 예외(Exception)를 발생시키고, 이를 프론트엔드(클라이언트)에게 통일된 규격으로 응답하기 위한 표준 가이드입니다.

## **1\. 예외(Exception)의 계층적 분리 원칙**

가장 중요한 원칙은 \*\*"도메인 계층과 애플리케이션 계층은 자신이 웹 환경(HTTP)에서 실행되는지 몰라야 한다"\*\*는 것입니다. 따라서 비즈니스 로직 내부에서 NestJS의 HttpException, BadRequestException 등을 직접 던지는 행위를 엄격히 금지합니다.

### **1.1. Base 커스텀 예외 클래스**

모든 커스텀 예외는 시스템의 BaseException을 상속받아 생성합니다. 계층별로 던질 수 있는 예외의 종류를 제한합니다.

* **🟢 DomainException:** 비즈니스 룰 위반 시 발생 (예: InvalidAssignmentStatusException)  
* **🟡 ApplicationException:** 유스케이스 흐름 제어 오류 시 발생 (예: EntityNotFoundException)  
* **🔵 InfrastructureException:** 외부 통신 실패, DB 타임아웃 등 인프라 에러 시 발생 (예: ExternalApiTimeoutException)

### **1.2. 도메인 계층 예외 처리 예시**

// ❌ 안티패턴 (도메인 계층이 HTTP 상태 코드를 알고 있음)  
if (this.status \!== 'PENDING') {  
  throw new BadRequestException('진행 중인 프로젝트가 아닙니다.');   
}

// 🟢 표준 패턴 (순수 비즈니스 예외만 발생)  
if (this.status \!== 'PENDING') {  
  throw new InvalidProjectStatusException(this.id, this.status);   
}

// domain/exceptions/invalid-project-status.exception.ts  
export class InvalidProjectStatusException extends DomainException {  
  constructor(projectId: string, currentStatus: string) {  
    super(  
      'ERR\_PROJECT\_INVALID\_STATUS', // 사전에 정의된 표준 에러 코드  
      \`프로젝트(${projectId})의 현재 상태(${currentStatus})로는 해당 작업을 수행할 수 없습니다.\`  
    );  
  }  
}

## **2\. 표준 에러 응답 포맷 (Error Payload)**

어떤 도메인에서 예외가 발생하든, 클라이언트(프론트엔드, 타 시스템)가 받는 JSON 응답 형태는 100% 동일해야 합니다. 이를 통해 프론트엔드는 하나의 에러 처리 인터셉터만 구현하면 됩니다.

### **2.1. 표준 JSON 응답 스펙**

{  
  "success": false,  
  "error": {  
    "code": "ERR\_ASSIGNMENT\_ALREADY\_COMPLETED",  
    "message": "이미 완료된 배정 건은 수정할 수 없습니다.",  
    "traceId": "req-123e4567-e89b-12d3-a456-426614174000"  
  },  
  "timestamp": "2026-04-24T10:14:00.000Z",  
  "path": "/api/v1/assignments/123"  
}

* **code**: 문자열 기반의 고유 에러 코드 (프론트엔드 다국어 처리 및 분기 로직용)  
* **message**: 개발자 및 사용자 참고용 명확한 에러 메시지  
* **traceId**: 로그 추적을 위한 고유 ID. 고객이 에러를 제보할 때 이 ID만 주면 백엔드 개발자가 즉시 로그를 찾을 수 있어야 함.

## **3\. 전역 예외 필터 (Global Exception Filter)**

비즈니스 로직(Service)에서 던져진 순수 DomainException을 잡아, HTTP 상태 코드(Status Code)와 표준 JSON 포맷으로 변환하는 최종 방어막입니다. NestJS의 ExceptionFilter를 활용합니다.

### **3.1. 에러 매핑 룰 (Mapping Rule)**

필터는 에러의 타입(Type)을 보고 적절한 HTTP 코드를 자동으로 매핑합니다.

* DomainException \-\> **400 (Bad Request)** 또는 **422 (Unprocessable Entity)**  
* EntityNotFoundException \-\> **404 (Not Found)**  
* UnauthorizedException \-\> **401 (Unauthorized)**  
* InfrastructureException 등 알 수 없는 에러 \-\> **500 (Internal Server Error)**

### **3.2. GlobalExceptionFilter 구현 뼈대**

@Catch()  
export class GlobalExceptionFilter implements ExceptionFilter {  
  catch(exception: unknown, host: ArgumentsHost) {  
    const ctx \= host.switchToHttp();  
    const response \= ctx.getResponse\<Response\>();  
    const request \= ctx.getRequest\<Request\>();  
      
    // Request 객체에 미들웨어를 통해 미리 주입된 traceId 추출  
    const traceId \= request.headers\['x-trace-id'\] || 'unknown-trace-id';

    let status \= HttpStatus.INTERNAL\_SERVER\_ERROR;  
    let code \= 'ERR\_INTERNAL\_SERVER';  
    let message \= '서버 내부 오류가 발생했습니다.';

    // 예외 타입에 따른 매핑 처리  
    if (exception instanceof DomainException) {  
      status \= HttpStatus.BAD\_REQUEST;  
      code \= exception.errorCode;  
      message \= exception.message;  
    } else if (exception instanceof HttpException) {  
      // DTO Validation 실패 등 프레임워크가 던지는 HTTP 예외 처리  
      status \= exception.getStatus();  
      const res \= exception.getResponse() as any;  
      code \= \`ERR\_HTTP\_${status}\`;  
      message \= res.message || exception.message;  
    } 

    // 에러 로깅 (500 에러는 Stack Trace 포함, 400 에러는 Info/Warn 레벨)  
    if (status \>= 500\) {  
      Logger.error(\`\[${traceId}\] ${message}\`, (exception as Error).stack, 'ExceptionFilter');  
    } else {  
      Logger.warn(\`\[${traceId}\] ${message}\`, 'ExceptionFilter');  
    }

    // 표준 포맷으로 응답 전송  
    response.status(status).json({  
      success: false,  
      error: { code, message, traceId },  
      timestamp: new Date().toISOString(),  
      path: request.url,  
    });  
  }  
}

## **4\. 인프라 경계에서의 예외 감싸기 (Exception Wrapping)**

외부 라이브러리나 인프라(DB, Redis, Kafka)에서 발생하는 Native Error(예: QueryFailedError, TimeoutError)를 도메인이나 애플리케이션 계층으로 그대로 전파해서는 안 됩니다.

### **4.1. 어댑터(Adapter) 패턴에서의 예외 전환**

Adapter 계층(Repository 등)은 외부 기술의 에러를 캐치하여 의미 있는 ApplicationException이나 InfrastructureException으로 변환(Wrapping)하여 던져야 합니다.

// \[Adapter\] DB 제약 조건 위반 에러를 비즈니스 의미가 있는 에러로 전환  
async save(assignment: ManagerAssignment): Promise\<void\> {  
  try {  
    await this.db.insert(assignments).values(assignment.toSnapshot());  
  } catch (error) {  
    if (error.code \=== 'ER\_DUP\_ENTRY') { // MySQL 고유 에러 코드  
      // 외부 기술의 에러를 도메인이 이해할 수 있는 에러로 변환  
      throw new DuplicateAssignmentException(assignment.id);   
    }  
    // 그 외 예상치 못한 에러  
    throw new DatabaseInfrastructureException('DB 저장 중 오류 발생', error);  
  }  
}
