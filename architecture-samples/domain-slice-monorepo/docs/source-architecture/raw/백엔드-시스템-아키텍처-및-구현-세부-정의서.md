# **백엔드 시스템 아키텍처 및 구현 세부 정의서 (Developer Manifesto)**

본 문서는 우리 백엔드 시스템의 견고함, 확장성, 그리고 유지보수성을 보장하기 위한 **데이터 흐름 및 상태 제어의 핵심 구현 규칙**을 정의합니다. 모든 개발자는 새로운 도메인을 추가하거나 기존 로직을 수정할 때 본 문서의 원칙을 반드시 준수해야 합니다.

## **0\. 핵심 용어 정의 (Glossary)**

본 규약 전반에서 사용되는 헥사고날 아키텍처(Ports and Adapters) 및 DDD(도메인 주도 설계) 관련 핵심 용어입니다.

* **Application Service (애플리케이션 서비스):** 사용자의 요청(Use Case)을 받아 비즈니스 로직의 흐름을 제어하고 오케스트레이션하는 중심 계층입니다. 외부 인프라 기술(DB, 메시지 큐 등)에 대한 어떠한 의존성도 가지지 않는 '순수성'을 유지해야 합니다.  
* **Port (포트):** Application Service가 외부 세상(DB, API, 메시지 큐 등)과 소통하기 위해 도메인 계층 내부에 정의한 \*\*'인터페이스(계약서)'\*\*입니다. 실제 구현 기술을 모르는 상태로 입출력 명세(추상 클래스 등)만 정의합니다.  
* **Adapter (어댑터):** Port(계약서)의 명세를 만족시키기 위해 특정 인프라 기술(예: Drizzle ORM, Redis, Kafka)을 사용하여 **실제 구현한 클래스**입니다. 철저히 외부 인프라스트럭처 계층에 격리되며 런타임에 주입(DI)됩니다.  
* **Command / Query (명령/조회):** 데이터의 상태를 변경하는 의도를 가진 요청(Command)과, 상태 변경 없이 단순히 데이터를 읽어오는 요청(Query)을 의미하며, 당사 시스템에서는 이 두 흐름을 완벽히 분리(CQRS)합니다.  
* **Outbox (아웃박스):** 시스템 장애 시 이벤트 유실을 막기 위해, 비즈니스 데이터가 변경되는 동일한 데이터베이스 트랜잭션 내에서 발행할 이벤트를 임시로 저장해 두는 테이블입니다.

## **1\. 데이터 흐름의 철저한 격리 (Strict CQRS 구현)**

시스템의 복잡도를 낮추고 성능을 극대화하기 위해, 데이터를 '변경하는 행위(Write)'와 '조회하는 행위(Read)'의 경로를 물리적, 논리적으로 완벽히 분리합니다.

### **1.1. Command (쓰기/명령) 규칙**

* **목적형 DTO:** 모든 쓰기 요청은 파라미터의 나열이 아닌, 행위의 목적이 명확한 DTO (예: AssignManagerCommand) 형태로 인입되어야 합니다.  
* **자체 검증:** Command DTO 내부에는 1차 유효성 검사(Validation) 로직이 포함되어야 합니다.  
* **인터페이스 분리:** 트랜잭션의 크기와 실패 전략이 다르므로, 단건 처리(ExecutionPort)와 대량 처리(ManagementPort) 인터페이스를 명확히 분리합니다. 대량 처리(Bulk)는 단건 실패가 전체 실패로 이어지지 않도록 **부분 성공(Partial Success)** 전략을 채택합니다.  
* **타겟 DB:** 오직 Command 서비스만을 통해 \*\*Primary DB (RDB)\*\*의 상태를 변경합니다.

### **1.2. Query (읽기/조회) 규칙**

* **무결성 보장:** 데이터를 조회하는 QueryPort 및 관련 서비스 로직에는 상태를 변경하는(Insert/Update/Delete) 코드가 1%도 포함되어서는 안 됩니다.  
* **Read Model 지향:** 복잡한 검색 및 대규모 조회는 Primary DB에 무거운 JOIN을 걸지 않고, \*\*비정규화된 Read DB (Redis, ElasticSearch 등)\*\*에서 가져오는 것을 최우선 원칙으로 합니다.  
* **DTO 분리:** 부득이하게 Primary DB를 읽더라도, Write 모델용 Entity를 그대로 반환하지 않고 전용 Read DTO로 매핑하여 반환합니다.

## **2\. 도메인 간 통신 규약 (Bounded Context & In-Process API)**

각 도메인은 독립된 마이크로서비스처럼 동작해야 합니다. 타 도메인의 데이터베이스나 내부 구현체에 대한 직접적인 접근은 시스템 결합도를 높이는 최악의 안티패턴으로 규정합니다.

### **2.1. 절대 금지 사항 (격리 파괴)**

* **남의 DB 직접 접근 금지:** A 도메인이 B 도메인의 테이블을 직접 쿼리하거나 JOIN 하는 행위는 어떠한 예외도 허용하지 않습니다.  
* **구현체 직접 참조 금지:** 타 도메인의 내부 Service, Repository, Entity 클래스를 import 하여 사용하는 것을 금지합니다.

### **2.2. 인프로세스 통신 (In-Process Call) 표준**

* **계약 기반 통신:** 타 도메인의 데이터가 필요할 경우, 해당 도메인이 명시적으로 외부에 열어둔 \*\*추상 클래스 기반의 QueryPort와 Read DTO\*\*만 임포트합니다.  
* **의존성 주입 (DI):** 런타임에 NestJS의 DI 컨테이너를 통해 해당 Port의 구현체를 주입받아 메모리 상에서 메서드를 호출합니다. (네트워크 오버헤드 없는 API 통신 효과)

### **2.3. 비동기 상태 전파 (Event-Driven)**

* 내 도메인의 상태 변경 사실을 타 도메인에 알릴 때는 직접 API(메서드)를 호출하지 않습니다.  
* 오직 \*\*Kafka (또는 내부 Event Bus)\*\*에 이벤트를 발행(Produce)하는 것으로 책임을 종료하며, 이를 구독하는 쪽에서 알아서 처리하도록(Choreography) 구성합니다.

## **3\. 이벤트 처리의 관문화 (Event Gateway & Outbox)**

이벤트를 단순히 데이터를 던지는 파이프가 아닌, 시스템의 추적성과 무결성을 보장하는 강력한 '관문'으로 취급합니다.

### **3.1. 이벤트 유실 방지 (Transactional Outbox)**

* 비즈니스 로직(App Service) 성공 직후 Kafka 프로듀서를 직접 호출하는 것을 금지합니다. (네트워크 지연 시 DB 롤백 불가 문제 발생)  
* 도메인 상태 변경 시, 동일한 RDB 트랜잭션 내에서 **Outbox 테이블에 이벤트를 함께 저장**하는 것까지만 수행합니다. 이후 별도의 릴레이 워커가 Outbox 테이블을 읽어 안전하게 이벤트를 발행합니다.

### **3.2. AOP 기반 이벤트 핸들러 (Consumer)**

* Kafka 이벤트를 수신하는 워커(Consumer Controller)는 HTTP API 컨트롤러와 동일한 아키텍처 방어막을 갖춰야 합니다.  
* **관심사 분리:** 권한 검증, 페이로드 구조 검증, 로깅 및 분산 추적(traceId 전달)은 모두 \*\*AOP Декоратор (@UseGuards, @UseInterceptors, @UsePipes)\*\*를 통해 외곽에서 선언적으로 처리합니다. 이벤트 핸들러 내부에는 순수 비즈니스(또는 Read DB 갱신) 로직만 남깁니다.

## **4\. 명시적 분산 트랜잭션과 동시성 제어 (Saga & Lock)**

분산 환경에서 데이터의 정합성을 보장하기 위해 실패 상황과 레이스 컨디션을 코드로 명시하고 방어합니다.

### **4.1. 락(Lock) 스코프의 비즈니스화**

* DB Row 기준(ID)의 락이 아닌, **비즈니스 목적을 나타내는 복합 키** (예: \[프로젝트ID\] \+ \[과정ID\] \+ \[공정유형ID\])를 락의 단위로 정의합니다.  
* **이중 방어선:** AOP 기반의 분산 락(Redis SetNX)으로 애플리케이션 레벨의 동시성을 1차 제어하고, Primary DB의 논리적 Unique 제약조건으로 최종 무결성을 강제합니다.

### **4.2. 명시적 롤백 (Saga Orchestration)**

* 여러 도메인에 걸친 트랜잭션 흐름은 중앙 통제자(Orchestrator 또는 Temporal 엔진)를 통해 상태 머신(State Machine)으로 관리합니다.  
* 트랜잭션 중 특정 도메인 로직이 실패할 경우, 이전에 성공했던 도메인의 데이터를 되돌리기 위해 \*\*보상 트랜잭션(Compensating API/Command, 예: '배정 취소')\*\*을 명시적으로 선언하고 호출하여 전체 시스템을 일관성 있게 복구합니다.

## **5\. 인프라 의존성 역전 (Adapter 추상화)**

도메인 로직(Application Service)은 언제든 교체될 수 있는 외부 인프라 기술로부터 완벽하게 보호받아야 합니다.

### **5.1. 도메인의 순수성 유지**

* Application Service 코드 내부에는 특정 DB 기술(Drizzle, TypeORM), 캐시(Redis), 메시지 브로커(Kafka) 등에 종속적인 라이브러리 import 구문이 절대 포함되어서는 안 됩니다.

### **5.2. Port와 Adapter를 통한 위임**

* Service는 DB 접근이나 외부 연동이 필요할 때, 오직 자신이 정의한 \*\*인터페이스 (Port)\*\*만 호출합니다.  
* 실제 인프라 기술을 사용하는 코드(**Adapter**)는 Infrastructure 계층에 별도로 작성하며, 이 Adapter가 Port 인터페이스를 구현(implements)하도록 합니다. DI를 통해 런타임에 결합되어, 도메인 코드 수정 없이 인프라 기술을 자유롭게 교체할 수 있는 구조를 확립합니다.
