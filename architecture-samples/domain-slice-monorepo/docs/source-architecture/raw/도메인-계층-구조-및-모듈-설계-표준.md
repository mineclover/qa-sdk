# **아키텍처 설계서: 도메인 계층 구조 및 모듈 설계 표준**

본 문서는 복잡한 계층 구조(예: 학교/학년/반)를 가진 도메인을 처리할 때의 모듈 설계 원칙과, 깊어지는 경로 및 유틸리티 관리를 위한 디렉터리 표준을 정의합니다. 본 아키텍처는 **포트와 어댑터(Ports and Adapters) 패턴**을 기반으로 한 **도메인 중심 설계**를 지향합니다.

## **1\. 모듈 설계 원칙 (Hierarchy Handling)**

### **1.1. 애그리거트(Aggregate) 정의 및 범위 설정**

애그리거트는 데이터 변경의 단위이자 일관성 경계(Consistency Boundary)입니다. 계층 구조가 깊은 도메인에서는 다음 패턴을 기준으로 범위를 설정합니다.

* **일관성 경계 우선:** "함께 변경되어야 하는가?"를 자문합니다. '반' 이름이 바뀔 때 '학생' 정보가 물리적으로 함께 변경되어야 하는 것이 아니라면, 둘은 별도의 애그리거트입니다.  
* **물리적 모듈 응집:** 모든 계층(학교, 학년, 반)을 개별 폴더로 쪼개어 격리하지 않습니다. 비즈니스 맥락이 같은 \*\*academic(학사)\*\*이라는 하나의 상위 모듈로 묶어 관리 효율성을 높입니다.  
* **ID 참조를 통한 결합도 완화:** 하위 객체는 상위 객체를 직접 소유(Inclusion)하지 않고, 상위 객체의 ID(Value Object)를 참조(Reference)하는 방식을 취합니다.

### **1.2. 단위 관리 애그리거트 설계 패턴**

단위(Unit)가 계층적일 때(학년 \> 반), 요구사항에 따라 애그리거트 루트를 다르게 정의합니다.

1. **단위별 게시판 (Unit-based Boards):**  
   * **패턴:** Board를 독립적인 애그리거트로 분리하고, OwnerId(학년ID 또는 반ID)와 UnitType(GRADE, CLASS)을 속성으로 가집니다.  
   * **이유:** 게시판의 생명주기는 학급 정보의 변경 주기와 일치하지 않으므로 독립적 관리가 유리합니다.  
2. **그룹별 규칙 관리 (Rule-based Grouping):**  
   * **시나리오:** 1\~5반은 A 선생님, 6\~10반은 B 선생님을 교과목 담당으로 배정.  
   * **패턴:** SubjectAssignmentRule이라는 별도의 애그리거트를 정의합니다. 이 객체는 GradeId, ClassRange(1-5), TeacherId, SubjectId를 가집니다.  
   * **이유:** 개별 '반' 엔티티에 선생님 정보를 넣으면 그룹 단위 규칙 변경 시 모든 반 엔티티를 수정해야 합니다. 규칙 자체를 하나의 단위(Aggregate)로 관리합니다.

## **2\. 표준 디렉터리 구조 (예시: 학사 관리 시스템)**

깊은 경로 문제를 해결하기 위해 **도메인별 서브 폴더**와 외부 노출을 위한 \*\*index.ts (Barrel Export)\*\*를 활용합니다.

* 📂 src/  
*  ┣ 📂 common/                  \# 🛠 전역 공통 유틸리티 (도메인 무관)

*  ┃  
*  ┣ 📂 modules/                 \# 🏛 도메인 모듈 (Bounded Contexts)  
*  ┃ ┗ 📂 academic/              \# \[학사 관리 모듈\] 학교/학년/반/학생 포함  
*  ┃   ┣ 📂 domain/              \# 🟢 Core (Business Logic)  
*  ┃   ┃ ┣ 📂 student/           \# 학생 애그리거트  
*  ┃   ┃ ┃ ┣ 📜 student.entity.ts  
*  ┃   ┃ ┃ ┗ 📜 student.vo.ts    \# GradeId, ClassNo 등  
*  ┃   ┃ ┣ 📂 classroom/         \# 학급 애그리거트

*  ┃   ┃ ┃ ┗ 📜 subject-assignment-rule.entity.ts  
*  ┃   ┃ ┣ 📜 academic.exceptions.ts  
*  ┃   ┃ ┗ 📜 index.ts           \# Barrel Export: 외부 모듈은 여기만 import  
*  ┃   ┃  
*  ┃   ┣ 📂 application/         \# 🟡 Orchestration (Use Cases)  
*  ┃   ┃ ┣ 📂 student/           \# 학생 관련 유스케이스 (Commands/Queries)  
*  ┃   ┃ ┣ 📂 assignment/        \# 배정 규칙 관련 유스케이스

## **3\. 유틸리티 및 경로 관리 규약**

### **3.1. 유틸리티의 위치 결정**

1. **Global Utility (src/common/utils):** 도메인 지식이 없는 순수 기술 유틸리티 (예: string-helper.ts).  
2. **Domain Utility (src/modules/{domain}/domain/helpers):** 특정 도메인 규칙이 섞인 계산 로직 (예: grade-promotion-logic.ts).

### **3.2. Alias 사용 강제 (Deep Path 방지)**

../../../../와 같은 상대 경로 사용을 금지하고 tsconfig.json에 정의된 경로 별칭을 사용합니다.

* @common/\* \-\> src/common/\*  
* @modules/\* \-\> src/modules/\*

## **4\. 계층 조회(Cross-Aggregate Query) 구현 방식**

학교 \> 학년 \> 반을 거쳐 학생을 찾는 것과 같은 복잡한 계층 조회는 다음과 같이 처리합니다.

1. **쓰기(Command):** Student 엔티티 내부에 상위 식별자(SchoolId, GradeId, ClassId)를 필드로 저장하여 각 객체가 자신의 위치 정보를 직접 갖게 합니다.  
2. **조회(Query):** application/queries 계층에 \*\*StudentSearchService\*\*를 만듭니다. 이 서비스는 DB의 인덱싱된 컬럼을 사용하여 한 번의 쿼리로 결과를 가져옵니다.  
   * *주의:* 조회를 위해 상위 엔티티부터 순차적으로 로드하는 방식은 지양하며, 필요 시 비정규화된 **Read Model**을 활용합니다.

## **5\. 요약: 복잡도 대응 전략**

* **캡슐화:** 외부 모듈은 타 도메인의 domain/이나 infrastructure/ 내부 폴더를 직접 뒤지지 않고, index.ts나 application/ports를 통해서만 소통합니다.  
* **폴더 깊이 제한:** 논리적으로 연관된 하위 개념은 폴더를 무한정 나누기보다 파일명 접두사로 구분하거나 한 단계의 서브 폴더 내에서 관리합니다.  
* **테스트 용이성:** 모든 클래스와 함수는 외부(\*.spec.ts)에서 접근 가능하도록 명시적으로 export 되어야 합니다.
