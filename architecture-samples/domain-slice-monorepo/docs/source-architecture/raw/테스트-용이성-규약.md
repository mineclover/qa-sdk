# **아키텍처 설계서: 테스트 용이성을 위한 코드 작성 규약 (Design for Testability)**

본 문서는 architecture\_testing\_strategy.md에 정의된 테스트를 원활하게 수행하기 위해, **실제 프로덕션 코드(Service, Domain 등)를 어떻게 작성하고 Export 해야 하는지**에 대한 실무 코딩 규약을 정의합니다.

테스트하기 어려운 코드는 곧 유지보수하기 어려운 코드입니다.

## **1\. 명시적인 의존성 주입 (Dependency Injection 강제)**

테스트 코드에서 서비스 계층을 생성할 때, 실제 DB 대신 Mock 객체를 밀어 넣을 수 있으려면 \*\*모든 외부 의존성이 생성자를 통해 주입(Injection)\*\*되어야 합니다.

### **🔴 Anti-Pattern (테스트 불가)**

클래스 내부에서 new 키워드로 인프라 객체를 직접 생성하거나, 전역 컨테이너를 직접 참조하면 테스트 코드에서 이를 가로채서 Mocking할 방법이 없습니다.

export class AssignManagerService {  
  private repository: AssignmentDrizzleRepository;

  constructor() {  
    // 내부에서 직접 생성해버리면 테스트 시 MockRepository로 교체할 수 없음  
    this.repository \= new AssignmentDrizzleRepository();   
  }  
}

### **🟢 Standard Pattern (테스트 용이)**

의존성은 반드시 **Port(인터페이스)** 타입으로 생성자를 통해 주입받아야 합니다.

export class AssignManagerService {  
  constructor(  
    // 인터페이스(Port)에만 의존하므로, 테스트 코드에서 Mock 객체를 쉽게 주입 가능  
    @Inject(ASSIGNMENT\_REPOSITORY\_PORT)  
    private readonly repository: AssignmentRepositoryPort,  
  ) {}  
}

## **2\. 모듈의 명시적 Export (Named Export 권장)**

테스트 파일에서 프로덕션 코드를 정확하고 안전하게 import 하기 위해, 파일 단위의 Export 규칙을 통일합니다.

### **🔴 Anti-Pattern (Default Export)**

export default를 사용하면 import 하는 쪽에서 임의로 이름을 바꿀 수 있어, 리팩토링이나 Mocking 시 연결 고리를 찾기 어려워집니다.

// service.ts  
export default class AssignManagerService { ... }

// test.ts  
import MyCustomService from './service'; // 이름이 달라져 추적이 어려움

### **🟢 Standard Pattern (Named Export)**

모든 클래스, 인터페이스, 상수는 반드시 **Named Export**를 사용합니다.

// service.ts  
export class AssignManagerService { ... }

// test.ts  
import { AssignManagerService } from './service'; // 정확한 심볼 매칭

## **3\. 제어할 수 없는 외부 요인의 추상화 (시간, 난수 등)**

테스트는 "언제, 어디서 실행하든" 항상 동일한 결과를 내야 합니다(결정론적 실행). new Date()나 Math.random() 같은 코드가 비즈니스 로직에 하드코딩되어 있으면 테스트 결과를 단언(Assert)하기 매우 어렵습니다.

### **🔴 Anti-Pattern**

export class AssignmentEntity {  
  public assignManager(managerId: string) {  
    this.managerId \= managerId;  
    // 테스트 실행 시점마다 시간이 달라져서 expect(assignedAt).toBe(...) 검증 불가  
    this.assignedAt \= new Date();   
  }  
}

### **🟢 Standard Pattern**

시간이나 난수 등 변동성이 있는 값은 **외부에서 주입(Parameter)** 받거나, 이를 제공하는 **추상화된 Provider**를 사용해야 합니다.

export class AssignmentEntity {  
  // 시간을 외부(Service)에서 주입받아 객체의 순수성 유지  
  public assignManager(managerId: string, assignedAt: Date) {  
    this.managerId \= managerId;  
    this.assignedAt \= assignedAt;  
  }  
}

// 테스트 코드에서의 활용  
it('배정 일시가 정확히 기록되어야 한다', () \=\> {  
  const fixedDate \= new Date('2026-04-24T10:00:00Z');  
  assignment.assignManager('manager-1', fixedDate);  
    
  expect(assignment.assignedAt).toEqual(fixedDate); // 완벽한 단언(Assert) 가능  
});

## **4\. 전역 상태(Global State) 및 Singleton 지양**

Node.js 환경에서 모듈 레벨의 전역 변수나 정적(Static) Singleton 인스턴스를 사용하면, 테스트 케이스 간에 상태가 오염되어 \*\*Flaky Test(어쩔 땐 성공하고 어쩔 땐 실패하는 테스트)\*\*의 주범이 됩니다.

### **🔴 Anti-Pattern**

// global-store.ts  
export const GlobalConfig \= { isMaintenanceMode: false };

// service.ts  
export class MyService {  
  execute() {  
    if (GlobalConfig.isMaintenanceMode) throw new Error();  
  }  
}

### **🟢 Standard Pattern**

상태를 가지는 모든 객체는 NestJS의 DI 컨테이너 관리를 받는 **Provider(Injectable)** 형태로 작성하여, 테스트 코드(또는 Test Module)가 실행될 때마다 새롭게 격리된 인스턴스가 생성되도록 해야 합니다.
