# **아키텍처 설계서: 계층별 테스트 전략 (Testing Strategy)**

본 문서는 헥사고날 아키텍처(Ports & Adapters) 환경에서 코드의 변경에 대한 안정성을 확보하고, CI/CD 파이프라인의 실행 속도를 극대화하기 위한 **계층별 표준 테스트 작성 규약 및 트래픽 격리 전략**을 정의합니다.

특히 DB 접근 여부와 원자성(Atomicity) 검증의 책임을 명확히 분리하여 테스트의 목적을 세분화합니다.

## **1\. 테스트 피라미드와 트래픽 격리 전략 (Traffic Separation)**

테스트 간의 간섭(Flaky Tests)을 막고 실행 속도를 최적화하기 위해, 테스트 트래픽을 파일 확장자, 실행 명령어, 그리고 의존성(DB 접근 여부) 기준으로 완벽히 격리합니다.

| 테스트 분류 | 타겟 계층 | 확장자 컨벤션 | DB 접근 여부 | 의존성 및 실행 환경 |
| :---- | :---- | :---- | :---- | :---- |
| **Domain Unit Test**(순수 로직 검증) | Domain | \*.spec.ts | **절대 불가** | 외부 의존성 없음, Mocking 불필요 (초고속 메모리 실행) |
| **Service Unit Test**(오케스트레이션 검증) | Application | \*.spec.ts | **절대 불가** | 외부 의존성 없음, **Port(인터페이스) Mocking 필수** |
| **Integration Test**(물리적 원자성 검증) | Infrastructure | \*.int.spec.ts | **접근 필수** | Testcontainers (격리된 Docker DB 환경) |
| **E2E Test**(전체 사이클 검증) | Presentation, 전체 흐름 | \*.e2e.spec.ts | **접근 필수** | 전용 E2E DB, 가상 클라이언트(Supertest) 기반 |

* **CI/CD 파이프라인 적용:** \* 로컬 커밋 및 PR 생성 시: npm run test (단위 테스트만 실행, 수십 초 내 완료하여 Fail-fast 보장)  
  * main 브랜치 머지 및 배포 시: test:int, test:e2e까지 전체 실행 (수 분 소요 허용)

## **2\. 도메인 계층 단위 테스트 (Domain Unit Test \- 순수 로직)**

가장 중요하고 가장 빠르게 실행되어야 하는 테스트입니다. 어떠한 프레임워크(NestJS) 종속성이나 가짜 객체(Mock)도 필요하지 않습니다.

### **2.1. 테스트 원칙**

* **순수성 강제:** DB, Redis, Kafka 등을 세팅할 필요가 없습니다. 순수 TypeScript 객체(Entity)의 인스턴스를 직접 new 키워드로 생성하고 메서드를 호출하여 상태 변화를 검증합니다.  
* **행위 중심 검증:** 단순히 속성(Property) 값이 할당되었는지를 확인하는 것이 아니라, 비즈니스 룰(Invariant)이 지켜지고 도메인 예외(DomainException)가 정상적으로 터지는지를 중점적으로 검증합니다.

### **2.2. 구현 예시 (Jest / Vitest)**

describe('ManagerAssignment (Domain Entity)', () \=\> {  
  it('이미 완료된 배정 건에 담당자를 재배정하면 예외가 발생한다', () \=\> {  
    // Given: 완료 상태의 엔티티 직접 생성 (Mock DB 불필요)  
    const assignment \= new ManagerAssignment('id-1', processInfo, 'old-manager');  
    assignment.complete(); // 상태를 COMPLETED로 변경

    // When & Then: 재배정 시도 시 DomainException 발생 검증  
    expect(() \=\> {  
      assignment.assignManager('new-manager');  
    }).toThrow(InvalidAssignmentStatusException);  
  });  
});

## **3\. 애플리케이션 계층 단위 테스트 (Service Unit Test \- 오케스트레이션)**

유스케이스(Service)가 도메인 객체를 잘 오케스트레이션하고, 저장소(Port)를 올바른 순서로 호출하는지 검증합니다. **실제 DB 트랜잭션을 발생시키지 않으며, 논리적인 흐름만 검증합니다.**

### **3.1. 테스트 원칙**

* **Mocking 적극 활용:** 실제 DB 어댑터를 연결하지 않고, Service가 의존하는 Port(인터페이스)를 Mocking(가짜 객체)하여 테스트합니다.  
* **논리적 원자성(의도) 검증:** Service 계층의 테스트는 "DB에 진짜 데이터가 저장되었는가?"를 확인하는 곳이 아닙니다. 대신, **"정상 흐름에서 비즈니스 저장 함수와 이벤트 발행 함수가 둘 다 호출되었는가?"** 라는 오케스트레이션의 **의도**를 검증합니다.

### **3.2. 구현 예시**

describe('AssignManagerService', () \=\> {  
  let service: AssignManagerService;  
  let mockRepository: jest.Mocked\<AssignmentRepositoryPort\>;  
  let mockOutbox: jest.Mocked\<OutboxPort\>;

  beforeEach(() \=\> {  
    // DB와 메시지 큐를 대신할 Mock 객체 생성  
    mockRepository \= { findById: jest.fn(), save: jest.fn() };  
    mockOutbox \= { saveEvent: jest.fn() };  
    service \= new AssignManagerService(mockRepository, mockOutbox);  
  });

  it('담당자 배정이 성공하면 데이터 저장과 이벤트 적재가 모두 호출되어야 한다 (논리적 원자성)', async () \=\> {  
    // Given  
    mockRepository.findById.mockResolvedValue(new ManagerAssignment('id-1', ...));  
      
    // When  
    await service.execute(new AssignManagerCommand('proj-1', 'manager-2'));

    // Then: 실제 DB 저장이 아닌, "호출 의도"를 검증  
    expect(mockRepository.save).toHaveBeenCalledTimes(1);  
    expect(mockOutbox.saveEvent).toHaveBeenCalledTimes(1);  
  });  
});

## **4\. 인프라 계층 통합 테스트 (Integration Test \- DB 연동)**

실제로 DB에 접근하는 테스트 영역입니다. Service 계층에서 "호출 의도"만 검증했던 트랜잭션 원자성이 **물리적으로 완벽하게 동작하는지**를 검증합니다.

### **4.1. 물리적 원자성 및 DB 접근 원칙**

* **Testcontainers 의무 사용:** SQLite 등 가벼운 메모리 DB로 흉내 내는 것을 엄격히 금지합니다. 실제 운영 환경과 동일한 DB 엔진(PostgreSQL, Redis 등)을 Docker로 띄워주는 \*\*Testcontainers\*\*를 사용해야 실제 트랜잭션 락킹과 고유 쿼리 문법을 검증할 수 있습니다.  
* **트랜잭션/Outbox 물리적 검증:** DB 장애 발생 시 트랜잭션이 롤백되어 비즈니스 데이터와 Outbox 데이터가 \*\*동시에 저장 취소되는 물리적 원자성(ACID)\*\*을 여기서 증명해야 합니다.

### **4.2. 구현 예시**

describe('AssignmentDrizzleRepository (Integration)', () \=\> {  
  let db: DbType;  
  let container: StartedPostgreSqlContainer;

  beforeAll(async () \=\> {  
    // 가짜 객체가 아닌 실제 DB 인프라 구동  
    container \= await new PostgreSqlContainer().start();  
    db \= setupDrizzle(container.getConnectionUri());  
    await runMigrations(db);   
  });

  afterAll(async () \=\> await container.stop());

  it('비즈니스 데이터와 Outbox 이벤트가 단일 트랜잭션(ACID)으로 물리적 저장되어야 한다', async () \=\> {  
    const repository \= new AssignmentDrizzleRepository(db);  
    const assignment \= new ManagerAssignment('id-1', ...);  
      
    // When: 트랜잭션 기반 저장 메서드 실행  
    await repository.saveWithEvent(assignment, new ManagerAssignedEvent(assignment));

    // Then: 실제 DB에 쿼리를 날려 데이터가 동시에 적재되었는지 물리적 확인  
    const savedAssignment \= await db.select().from(assignments).where({ id: 'id-1' });  
    const savedOutbox \= await db.select().from(outboxEvents).where({ aggregateId: 'id-1' });  
      
    expect(savedAssignment.length).toBe(1);  
    expect(savedOutbox.length).toBe(1);  
  });  
});

## **5\. E2E 테스트 전략 (Client Mocking & Full Flow)**

E2E 테스트는 프론트엔드가 없는 상태에서도 **Mock 데이터 기반의 가상 클라이언트**를 구성하여, API 엔드포인트부터 실제 DB 저장 및 이벤트 적재까지의 전체 라이프사이클을 검증합니다.

### **5.1. E2E 클라이언트 Mocking 전략**

* **Headless Client (Supertest):** 실제 브라우저를 띄우지 않고, supertest 라이브러리를 통해 NestJS의 HTTP 레이어(Controller, Guard, Pipe)를 직접 타격하는 가상 클라이언트를 구축합니다.  
* **데이터 빌더 (Fixture Builder):** 클라이언트가 전송할 페이로드(JSON)를 하드코딩하지 않고, MockClientDataBuilder 패턴을 사용하여 유효한/유효하지 않은 요청 템플릿을 체계적으로 생성합니다.  
* **인증(Auth) 우회 또는 Mock 토큰:** 실제 인증 서버(SSO/OAuth)를 연동하지 않고, 테스트 전용 JwtStrategy를 띄우거나, E2E 환경 전용 '테스트 마스터 토큰'을 발급받아 헤더에 주입합니다.

### **5.2. E2E 구현 예시 (\*.e2e.spec.ts)**

import \* as request from 'supertest';  
import { INestApplication } from '@nestjs/common';

describe('Assignment API (E2E)', () \=\> {  
  let app: INestApplication;  
  let mockClientToken: string;

  beforeAll(async () \=\> {  
    // 실제 NestJS 앱 전체 가동 (DB는 Testcontainers 연결)  
    const moduleFixture \= await Test.createTestingModule({ imports: \[AppModule\] }).compile();  
    app \= moduleFixture.createNestApplication();  
    await app.init();  
      
    mockClientToken \= 'Bearer mock-test-admin-token';   
  });

  afterAll(async () \=\> await app.close());

  it('/api/assignments (POST) \- 클라이언트 배정 요청 정상 흐름', async () \=\> {  
    // Given: Mock 클라이언트 페이로드 생성 (빌더 패턴 활용)  
    const clientPayload \= new MockAssignmentPayloadBuilder()  
      .withProjectId('proj-123')  
      .withManagerId('user-999')  
      .build();

    // When: 가상 클라이언트(Supertest)가 HTTP 요청 발송  
    const response \= await request(app.getHttpServer())  
      .post('/api/assignments')  
      .set('Authorization', mockClientToken)  
      .send(clientPayload);

    // Then: 프론트엔드가 기대하는 표준 API 응답 검증  
    expect(response.status).toBe(201);  
    expect(response.body.success).toBe(true);  
  });  
});

## **6\. 요약 (Action Item)**

1. **테스트 책임의 분리:** \* Domain Unit: 비즈니스 룰이 정확한가? (DB 접근 X)  
   * Service Unit: 올바른 순서로 Port를 호출하는가? (DB 접근 X, Mock 활용)  
   * Integration: 실제 DB에서 트랜잭션/조회가 완벽히 동작하는가? (DB 접근 O)  
2. **테스트 분리 실행:** 위 세 가지 성격의 테스트는 서로 다른 jest.config 파일을 통해 명확히 분리하여 실행 속도를 확보하세요.  
3. **E2E는 사용자의 관점에서:** E2E 테스트는 내부 Service 로직이나 물리적 쿼리를 검증하는 곳이 아닙니다. 철저히 "클라이언트가 이 JSON을 보냈을 때, 기대하는 HTTP 응답이 오는가"에 집중하세요.
